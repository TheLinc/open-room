# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What Open Room is

A cross-platform (Windows + macOS) desktop app for running multiple named Claude Code agents concurrently. Each agent has its own model, tool/MCP access, TTS voice, and a persistent `.md` context file describing its role. Agents are addressed by voice (push-to-talk, or an opt-in wake word) or by typing in a per-agent chat pane. They report back via native notifications by default, or TTS when enabled.

Open Room is a **conversational layer over Claude Code**, not a task launcher wrapped around it. Agents are personas you talk to over days: named, voice-addressable, carrying a persistent role `.md`, and remembering prior conversations. That framing drives several decisions below — most visibly, conversations persist and resume by default.

Agents draw usage from the Claude Code account already logged in on the machine — the app never handles API keys. The Agent SDK ships its own `claude` binary, so no global Claude Code install is needed to run agents; what is needed is the login, which every CLI shares through `~/.claude`.

**This project is open source.** Consequences that affect real decisions:

- Every user brings their own Claude Code login. The app ships no credentials and never proxies anyone else's account; usage bills to whoever is logged in locally. Document this prominently — it's the first thing a new user needs to understand. (A global Claude Code install is how they sign in, not how agents run — see "Packaging".)
- Every model call goes through the Agent SDK / CLI path. Never import `@anthropic-ai/sdk` — a direct API client would need a key and would break the promise above. This applies to internal calls too, including the TTS fallback summarizer.
- Redistributing model binaries is a licensing question. Voices and STT models are downloaded at runtime from upstream, except the single bundled default voice whose license is verified (see "TTS voices and models").
- Everything stays local: no telemetry, no analytics, no phone-home.
- This file is public and contributor-facing. Write it for someone who has never seen the codebase.


## Architecture

Four process types plus an overlay window. The separation is load-bearing — don't collapse them.

```
Electron main (Node)            → AgentSupervisor, ConfigStore, SpeechBus, Router,
                                  HotkeyManager, VoiceController, AppTray
  ├─ IPC ──────────────────────→ Renderer (React + shadcn/ui)
  ├─ IPC ──────────────────────→ Listening overlay + working HUD (frameless, always-on-top,
  │                                click-through, owns the microphone)
  ├─ stdio JSON-RPC ───────────→ Voice sidecar (plain Node)
  └─ Agent SDK ────────────────→ N × claude CLI subprocesses (one per active agent)
```

**Electron main** (`src/main/`) owns all state and all agent lifecycles. The renderer holds no authoritative state.

**Renderer** (`src/renderer/`) is display and input only. Chat panes render agent output verbatim.

**Listening overlay** (`src/overlay/`) is a small always-on-top window with two modes: the listening pill during a voice interaction — which agent, which conversation, and what state — and a HUD of one pip per working agent whenever the main window is hidden or unfocused. It exists as a separate window because voice input is global and the working HUD outlives any one window; the main window is usually backgrounded when someone talks to an agent.

**It owns the microphone.** `getUserMedia` is a Chromium API, so capturing in the plain-Node sidecar would mean a native audio binding for something a renderer does for free. It opens its `AudioContext` at 16 kHz so Chromium does the resampling Whisper needs, collects samples in an `AudioWorklet` off the main thread, and sends finished audio to main as base64 PCM.

**Voice sidecar** (`src/voice/`) is a separate plain-Node process handling speech-to-text and TTS synthesis → audio out, plus the `ModelManager` that downloads voice and STT models. It runs outside Electron deliberately: `onnxruntime-node` and transformers.js are heavy and native-adjacent, and keeping them out of the Electron process avoids ABI rebuilds (painful on Windows) and keeps inference off the UI thread. The native key hook for true hold-to-talk belongs here too, when it lands.

**Agent subprocesses** are spawned by `@anthropic-ai/claude-agent-sdk`, which shells out to the `claude` CLI. Each is a full CLI process — memory adds up, so concurrency is capped (see "Quota and concurrency").

## Core design decisions

These were settled deliberately. Revisit them explicitly rather than drifting.

### Chat output is never altered

The chat pane shows exactly what Claude Code would show — no rewriting, truncation, or reformatting. Anything that needs different content for a different channel (speech, notifications) gets that content produced separately, never by post-processing the transcript.

This is a promise about _content_, not about keeping every message mounted in the DOM. Capping retained messages per pane is fine and necessary — `MAX_RETAINED_ENTRIES` bounds it, and rows use `content-visibility: auto` so off-screen ones cost nothing to lay out.

**Assistant prose is rendered as markdown; nothing else is.** `MarkdownText` (react-markdown + remark-gfm) draws the marks the model chose — terminal Claude Code renders markdown too, so this is presentation, not alteration. User bubbles, slash-command output and tool results stay verbatim text: a `**` the user typed is what they typed. Links carry `target="_blank"` because `setWindowOpenHandler` routes those to the OS browser, and a plain click would navigate the renderer itself away. Element styles live under `.markdown` in `main.css` — preflight strips every default and the typography plugin is not installed.

**A settled turn's activity folds behind one "Worked for 1m 35s" row.** The pattern is T3 Code's (`apps/web/src/components/chat/MessagesTimeline.logic.ts`, `deriveTurnFolds`, read from a clone on 2026-09-10): once a turn has settled, everything between the prompt and the turn's final text message folds behind a single muted row with a chevron, and clicking it unfolds. `foldTurns` in `lib/transcript-folds.ts` is the pure projection both the live list and persisted history go through. What stays visible: the prompt, the final assistant message (the last one in the turn carrying text), the files-changed receipt, permission prompts. What folds: tool calls and results, thinking, intermediate prose, compaction rows, tool calls after the final text, and the result row itself, whose cost moves onto the fold ("Worked for 5s · $0.0651"). That figure is the turn's own: `total_cost_usd` on a result is the session's running total, and the first cut put it on every fold unchanged, so three identical turns read $0.0671, $0.0756, $0.0841; `turnCost` shows the step from the previous result, and a total that fell (the session restarted) as is. The header's "4 turns · $0.0841" is that running total and says so on hover. The first version left the result row under the fold, and "Turn complete · 2 turns" beneath "Worked for 5s" said the same thing twice; the turn count is API round trips and was dropped from the fold. A turn with nothing to fold keeps its result row as before. A live turn never folds (activity streams as before; the row appears on the result). A stopped turn reads "You stopped after 12s", which the supervisor's `interrupted` stamp makes knowable. An errored turn does not fold at all, so what went wrong stays on screen. Duration runs from the prompt to the result: live, from `receivedAt`; on disk, from the `timestamp` the SDK passes through on session messages, which it does (measured: history turns showed "Worked for 1s" and "6s" after a reload), with a bare "Worked" if it ever does not. Expansion is local pane state, reset on remount, as T3's is. A folded entry is not mounted, the same DOM policy as the retained-entries cap: presentation, not alteration, and one click away.

**A live turn collapses too: one row per run of activity, the last one naming the current call.** T3 Code's `work-live` row (`MessagesTimeline.logic.ts`, read 2026-09-11): while a turn runs, its tool calls collapse into a single row that names only the latest call, in present tense, clickable to expand the full list mid-turn; elapsed time is a separate "Working for" row; subagents get one standalone card with a count and their internal calls never reach the chat; skills get no summary at all, only a chip for a `$skill` mention in prose. Open Room's version: `liveRows` in `transcript-folds.ts` keeps prose in place as it streams and folds every run of activity between one piece of prose and the next; the trailing run is `live: true` and its label comes from `liveActivityLabel` (`lib/live-activity.ts`), earlier runs from `pastRunLabel` ("2 calls", or "Thought"). The label names the latest top-level call in present tense while pending and past tense once answered ("Running `npm test`" then "Ran `npm test`"), so the row keeps a subject between calls; `describeToolUse` knows Bash, Read, Edit, Write, Grep, Glob, Skill, Task, WebFetch, WebSearch and shortens MCP names. Subagents are counted on the same row ("· 2 subagents working") from unresolved `Task` calls, and entries carrying `parent_tool_use_id` never drive the label. There is no "used skills" summary, in either app; the Skill tool reads as "Using skill x" on the live row and that is the one place a skill shows. The live row is keyed by its first entry, which is the key the settled fold uses, so a row opened mid-turn stays open on settle. The working strip at the base lost its tool name and the live row has a still amber dot rather than the strip's breathing glyph: the first cut gave both the glyph and both the tool, and the field report was two loading elements at the bottom of the chat. T3's split is the same, a working row with verb and time and a live row with the call. `runningTool` stays in `lib/working-indicator.ts`, tested and unused, in case the strip ever wants it back. Measured in the dev app on a three-tool turn: "Running `ls`" at 3 s, "Searched for *.md" at 4.5 s, then "Worked for 5s · $0.0671" at settle, and only the prompt and the one row ever on screen.

**Code has its own tokens, `--code` and `--code-border`.** Inline code, fenced blocks and tool output used `muted` at 40% over the page: a 97% grey on white in light mode and a 27% grey at 40% over 14.5% in dark, so neither read as a block. The tokens are a clear step off the page plus a border in each theme, and the tool-result `pre` uses the same pair so a snippet and a tool's output still read as one kind of thing. Measured after: `oklch(0.23)` on `oklch(0.32)` dark, `oklch(0.955)` on `oklch(0.9)` light.

**A working strip sits at the base of the chat while a turn runs.** The header's "Working" is true but flat: a minute-old turn looks like a second-old one, and nothing says whether the model is thinking or a tool is running. `WorkingIndicator` is anchored between the transcript and the composer (so it is on screen at any scroll position) and shows an amber breathing glyph, a verb, the elapsed time, and the tool in flight. The decisions are pure in `lib/working-indicator.ts`: `workingVerb` is seeded by the turn's start so re-renders never flicker and steps every 8 s so a long turn moves on; `runningTool` reads the live entries back to the last prompt for a `tool_use` with no `tool_result` after it, shortening `mcp__server__tool` to the tool; `turnStartedAt` is the `receivedAt` main stamped on the prompt entry, because the React compiler lint refuses `Date.now()` during render and the transcript already carries the answer. The component owns a one-second clock and nothing else, with no synchronous set on the busy edge (the first tick corrects the label). Under reduced motion the glyph slows rather than stops, as the overlay's pips do. Measured in the dev app over a short turn: "Scheming… 0s" through "7s", "· PowerShell" while the tool ran, strip gone on the result.

**Filter non-rendering messages out before the list, not inside the row.** Most `system` messages produce no visible output, but a wrapper element with `contain-intrinsic-size` still reserves its placeholder height — a run of silent messages leaves a large blank gap above the transcript. `isRenderable()` exists for this.

### Streaming input mode, one live session per agent

Each active agent is one long-lived `query()` call driven by an `AsyncGenerator<SDKUserMessage>`. User messages are pushed into that generator; the session stays alive between turns.

This is not interchangeable with single-message mode. Per the SDK docs, single-message mode does **not** support dynamic message queueing, real-time interruption, or natural multi-turn conversation. Three things Open Room requires — `interrupt()`, `setPermissionMode()`, and in-loop permission prompts — exist only in streaming input mode.

`resume: sessionId` is how you **open** a conversation; the streaming generator is what **drives** it once open. The two are complementary, not alternatives.

`AgentSupervisor` holds one `PushableQueue` per agent — an async generator that can be pushed into after `query()` has started, which is what makes streaming input mode usable when prompts arrive unpredictably.

**The SDK does not echo user input back on the output stream.** The transcript would show replies with nothing to reply to, so the supervisor emits the user's own message itself, in the SDK's message shape, before pushing it to the queue.

**An interrupt arrives as an error result.** `query.interrupt()` ends the turn with `subtype: 'error_during_execution'` and `is_error: true`, which is indistinguishable from a genuine failure without tracking that the user asked for it. The supervisor sets an `interrupting` flag so a deliberate stop returns the agent to `ready` rather than showing "needs attention".

**The pane has one Stop, and it means "end this turn". Ending the session is a menu item.** A user who clicks during a turn wants the agent stopped now; whether the process survives is a resource decision they should never have to make at that moment. The header used to show Interrupt and Stop side by side as if they were alternatives. T3 Code was checked for comparison: its composer's stop dispatches a turn interrupt, its session stop is reachable only through thread deletion and a 30-minute idle reaper, and for Claude its "interrupt" is in fact `query.close()`, a process kill, because `interrupt()` can be acknowledged while a background task keeps the CLI alive. Open Room keeps the cheap path: the header's Stop calls `interrupt()`, so the context stays loaded and the next prompt costs no spawn. "End session" sits in the pane's overflow menu with its cost in the item ("Frees the agent's process. The next prompt resumes from disk."), and stays reachable because the concurrency cap's error says to stop another agent.

**Both stops are bounded, and escalate to closing the process.** `query.interrupt()` resolves on acknowledgement, not on the turn ending, so `interrupt()` waits for the result (`turnWaiters` on the session, fired by any result and by the stream closing) for `INTERRUPT_GRACE_MS` and calls `stop()` if it never comes. `stop()` interrupts a running turn first (`stopNeedsInterrupt`), closes the queue, waits the same grace for the pump, and then `query.close()`s, which the SDK escalates from SIGTERM to SIGKILL. `settledWithin` (`src/shared/stop-plan.ts`) is the bounded wait, tested with fake timers. Measured before any of this: the session Stop pressed 8 s into a 1500-word essay left the agent `working` for another 18 s until the essay was complete, because closing the input only tells the CLI there will be no more prompts and it finishes the turn it is on; after, 52 ms to `ready` and 364 ms to `idle` on a turn that could not have finished on its own. Found while verifying that: when a session whose last turn was interrupted is closed, the SDK's query loop re-raises that turn's error result as `Claude Code returned an error result: [ede_diagnostic] ...`, which the pump classified as `crashed` on an agent now idle. `pumpFailureIsFault` keeps a stream that fails while `stop()` is closing it off the runtime; one that fails on its own is still reported. The escalation path itself has not been observed in the app, since no turn has yet refused to end after an acknowledged interrupt. The transcript row that closes a stopped turn reads "Stopped" in the muted tone: the supervisor stamps `interrupted` on the result's `TranscriptEntry` (it is the only party that knows the stop was asked for), and `resultRow` in `lib/transcript.ts` reads it. Before that, every press of Stop ended in a red "Ended: error_during_execution" row.

### Conversations persist and resume

One conversation = one SDK session. Conversations belong to an agent and persist across app restarts.

This reverses an earlier requirement ("chat history shouldn't persist, like terminal Claude Code"), which reasoned from a false premise. Terminal Claude Code _does_ persist — `claude --continue` resumes the most recent session and `claude --resume` opens a picker. What it actually does is **start fresh by default with resume available on demand**. That's a display default, not a storage policy.

For a conversational layer the display default should differ, because a persona that forgets everything between launches isn't conversational. So:

- **Launching selects each agent's most recent conversation**, rendered and scrolled to the bottom, with a quiet `Resumed · last active 2 days ago` divider. Talking or typing resumes that session.
- **A conversation switcher in the pane header** lists recent conversations by title, plus "New conversation."
- **New conversations are explicit, never automatic.** No idle timer, no auto-reset. Surprise amnesia is worse than a long thread, and the worklog (below) makes manual resets cheap.
- **Never auto-replay everything.** Render the tail and load earlier on scroll. Mark session boundaries visibly so resumed context is never ambiguous.
- **The active conversation title appears in the pane header and the listening overlay**, so voice input never lands in a context the user didn't realize they were in.

Build this on SDK primitives rather than parsing JSONL: `listSessions()` for the picker, `getSessionMessages()` for transcript loading, `renameSession()` / `tagSession()` for naming and scoping, `forkSession` to branch without losing the original.

**Conversations are scoped to an agent by tag, not by title.** `tagSession(id, 'open-room:<agentId>')` on session init; `listSessions` filters on it. Titles belong to the user — keying off them would make a renamed conversation vanish from its agent, and a workspace may also hold sessions from terminal Claude Code or another agent pointed at the same folder.

**The tag carries a per-agent `instance` as well as the id.** The id is a slug of the name, and deleting an agent removes its directory but not its transcripts, so an agent created later under the same name got the same tag and opened on the deleted one's chat (field report). `createAgent` in main stamps `instance` (`newAgentInstance`) and the tag becomes `open-room:<id>:<instance>`; `updateAgent` keeps whatever is on disk (`withStoredInstance`), since the editor form does not carry the field and a renderer must not be able to move an agent onto another's conversations. Agents from before the field have no instance and keep the bare tag, so their history stays. The old transcripts are left on disk, untouched: deleting an agent was never a decision to delete its history.

The tag was half of it. The renderer holds live transcript entries and the runtime keyed by agent id too, and neither was cleared on delete, so within one app run the recreated agent still opened on the deleted one's prompt, reply and turn count while `listConversations` correctly returned nothing. `AgentSupervisor.forget` now emits `transcriptCleared` and an empty runtime after dropping its own. Measured with Playwright over CDP against the dev app: before, the recreated pane showed the old prompt, "Stopped · 2 turns · $0.0009" and the MCP pill; after, "Nothing yet. Ask Eric to do something." with no stats, and 0 conversations listed.

**Do not set `title` on `query()`.** It lands in *both* `customTitle` and `summary`, so every conversation would carry the same name and the switcher would be useless.

**Prefer `firstPrompt` over `summary` for display.** The SDK's summary tracks the *latest* prompt, so a conversation renames itself as it goes and two can end up sharing a title. How a conversation started is stable and is how people recall it. Order is `customTitle || firstPrompt || summary`.

**Clear live transcript entries when the active conversation changes.** Streamed entries belong to the conversation that produced them; leaving them mounted shows the previous conversation's messages under the newly selected one. Main emits `transcriptCleared` for this — persisted history is then reloaded from disk.

**Which conversation an agent lands in is decided in main, never in the renderer.** It used to be a `useEffect` in `useConversations`: on opening a pane, an idle agent with nothing chosen was pointed at its most recent conversation. Three things were wrong with that at once, all found by driving the app. The hook lives in `App`, so `agentId` changes on a sidebar click while the list refreshes asynchronously, and for one render the previous agent's conversations sat under the new agent's id — the effect fired in that window and handed the second agent the first agent's session (measured: Juno's turn was appended to Atlas's transcript file, with Atlas's context). A prompt by voice reaches an agent nobody has opened, so it started a fresh conversation — amnesia by route. And "New conversation" cleared the choice on an idle agent, which is exactly the condition the effect re-selected the latest on, so it was undone immediately. `resumeTarget` in `src/shared/conversation.ts` holds the decision; `AgentSupervisor.resolveResume` applies it both on `selectAgent` (`ensureConversation`) and on a cold `send()`, and `setActiveConversation` records that a choice was made — including the choice of *no* conversation. The list in the hook is still stamped with the agent it was fetched for, so the wrong list is never rendered during the refresh.

**Leaving the active conversation while the agent works asks first.** Selecting another conversation, starting a new one, and archiving or deleting the active one all go through `supervisor.stop`, because an agent has one live session and which conversation it resumes is fixed at spawn; T3 Code avoids the question with a process per thread, the tradeoff the concurrency cap rules out here. That stop used to happen silently on a click in a dropdown, and the pane's live entries were cleared with it, so the interrupted turn was not even visible as stopped. `switchNeedsConfirm` (`lib/switch-guard.ts`, tested) says when to ask: `working`, `starting`, or a pending permission prompt, since switching away from a question the agent asked is the likeliest misclick. The switcher then shows the line and two buttons at the top of its own menu ("Janet is still working. Stop it and switch?", Stop and switch, Cancel) instead of running the action; idle and ready switch on the click as before, and rename, restore and actions on a non-active row never ask. Letting the turn finish and then switching was rejected: the view would show one conversation while the process ran another. Esc backs out one step, the confirm first and then the menu, which is what a modal would have bought and the one thing the strip lacked; the strip was kept over a modal because the click happens inside a transient menu, two overlays would stack, and the sidebar's Delete agent already asks in place. Measured in the dev app on a counting turn: the confirm appeared, Cancel left the agent `working`, and Stop and switch landed on the other conversation 1.5 s later with the agent `idle`, the process gone, and the menu closed.

**Persisted history is trimmed against the live list before rendering.** History is re-read on every pane mount (the pane is keyed by agent, so every switch) while live entries survive switches in `useSessions`, so after any live turn the disk copy already contains what the live list still holds — rendered naively, the turn appeared twice under a "Resumed" divider. `trimOverlap` in `src/shared/history-overlap.ts` cuts history at the first assistant message whose uuid the live list also carries, then drops the persisted prompt before it, because the prompt the supervisor emits itself has no uuid to match on. A prompt sent moments ago with no reply yet is matched as the last persisted entry with the same text; nothing earlier is ever matched by text.

**`getSessionMessages` paginates from the start**, so reaching the tail needs the total first. The full transcript is read in main (a cheap disk read) and only a bounded slice crosses IPC — rendering is what janks, not reading.

**Per-agent ephemeral mode** (`persistSession: false`) stays as a privacy option. State the tradeoff in the UI: nothing on disk, and the docs are explicit that such sessions **cannot be resumed later** — so no conversation history and no crash recovery. **"Clear history"** deletes transcripts explicitly, per conversation and per agent.

### A conversation can have its own git worktree

Opt-in per agent (`worktrees: true`, default off): each *new* conversation runs in a fresh `git worktree` of the workspace, so two agents — or an agent and the user — never edit one checkout. `src/shared/worktrees.ts` names things, `src/main/git.ts` runs git, `src/main/worktrees.ts` (`WorktreeManager`) decides, and the supervisor executes.

**Open Room manages the worktrees itself rather than passing the CLI's `--worktree` flag.** The bundled CLI (2.1.233 when this was written; the SDK's version number tracks the CLI it bundles, so `@anthropic-ai/claude-agent-sdk@0.3.x` ships Claude Code 2.1.x) has `-w, --worktree [name]`, but from the SDK it is reachable only via `extraArgs`; it branches from `origin/<default>` by default, so local uncommitted state is absent; it auto-removes the worktree on exit; and resuming into a removed worktree is undocumented. Four unknowns in a feature whose failure mode is "edits landed somewhere unexpected", against six git commands with known semantics that `git.test.ts` pins as argv and runs once against a real temp repo.

**Worktrees live under `<OPEN_ROOM_HOME>/worktrees/<agentId>/<slug>`, outside the repository.** Inside it, tsc, eslint and the `@` picker's walk would all see a nested copy of the project. Location does not matter to the SDK: `listSessions({ dir, includeWorktrees: true })` discovers worktree sessions with `git worktree list --porcelain` (read off `sdk.mjs`), so a session whose `cwd` was the worktree is found by listing the workspace. The store used to pass `includeWorktrees: false`; the tag filter already scopes by agent, so that was over-cautious. It also lists every recorded path explicitly, so a conversation whose worktree was pruned by hand still appears. The branch is `open-room/<agentId>/<slug>` from the workspace's current HEAD — what the user has checked out, uncommitted work excluded, unpushed commits included.

**A session id is only known once the init message arrives, so a worktree is created pending and committed on init.** `place()` runs before `query()` because `cwd` is fixed at spawn; the record (`sessionId → {path, branch, baseCommit}` in `~/.open-room/agents/<id>/worktrees.json`) is written when the CLI identifies the session. A session that dies before init has its worktree removed (`abandon`) rather than stranded where nothing can find it. Resume follows the record; a directory that has gone but whose branch survives is re-attached with `git worktree add <path> <branch>`; otherwise the agent runs in the workspace with `isolation: { kind: 'fallback', reason }`. Conversations from before the feature have no record and stay in the workspace. `AgentRuntime.isolation` is always reported and the pane header shows the branch (or the fallback reason, in amber) — silently editing a different checkout than the one on screen is the failure this whole design exists to prevent. `cwd` is read off the init message rather than assumed.

**Deleting a conversation runs `git worktree remove` without `--force`, then `git branch -d`.** A dirty worktree is refused by git and kept, and the message names the path; `-d` deletes only a merged branch. Measured end to end: a conversation that wrote an untracked file was deleted, its transcript and record went, and the worktree and branch stayed on disk. Nothing uncommitted or unmerged is ever destroyed by the app.

**The `@` picker, open-in-editor and the diff all resolve against the active conversation's checkout** (`checkoutFor` in `src/main/ipc.ts`), so they describe the files the agent is actually editing. The editor's switch asks main whether the folder is a git repository (`inspectWorkspace`) and says so inline, because a switch that silently does nothing is the class of failure this file keeps recording.

### Archiving is deletion with a grace period

Deleting a conversation is final, and deciding that for each of a dozen finished threads is why nobody tidies the switcher. Archive takes a conversation out of the list without that decision: it stays on disk, appears under a collapsed "Archived (n)" group in the switcher with a countdown, and can be restored until `archiveRetentionDays` (settings, default 30, 0 = never) runs out. The decisions are pure in `src/shared/archive.ts`; the record is `~/.open-room/agents/<id>/archive.json` (`ArchiveStore`, same shape as the worktree records); `ArchiveSweeper` runs 20 s after launch and hourly.

**The sweeper deletes through the same path as the switcher's delete.** `removeConversation` (`src/main/remove-conversation.ts`) is the one way a conversation leaves the disk: stop a live session on it, transcript before worktree (the transcript is keyed by the worktree's path), release the worktree without force so uncommitted work is refused and kept, and drop the archive record whichever way the rest went. A failed removal is logged and the sweep moves on.

**Archiving the active conversation is decided in main.** It stops the session and lands the agent in the most recent *live* conversation, or none; `latestActive` also replaces the bare `[0]` in `resolveResume`, so a launch-time resume never picks an archived conversation back up. Measured in the dev app: archive from the switcher row, the header read "New conversation", the group showed "Deletes in 30 days", Restore put it back, and `archive.json` went to `{}`.

**The countdown rounds up.** Floored, a conversation archived a minute ago under a 30-day window read "29 days"; under a day left reads "today".

**A pre-existing gap seen while verifying:** the switcher's list is fetched on pane mount and after its own actions only, so a conversation started by the agent's first turn does not appear until the pane remounts. Not fixed here.

### Settings and the agent editor are paged, with one rail

Both dialogs outgrew a single scroll. `DialogNav` (`components/dialog-nav.tsx`) is the shared left rail; the page lists and the routing decisions live in `lib/dialog-pages.ts`, tested: which page a "turn it on in Settings" link opens on (`pageForHighlight`), and which editor pages hold a field with a validation error (`flaggedPages`), so a failed save marks the rail and jumps to the first flagged page rather than failing silently on a page the user cannot see. Settings pages: General, Voice, Conversations, Appearance, Updates. ### `WORKLOG.md` is what makes new conversations cheap

Each agent maintains a `WORKLOG.md` in its workspace, instructed via its `AGENT.md`. Its job is not to substitute for persistence — persistence exists. Its job is continuity _across_ conversations:

- **New conversation = fresh context window, but the agent still knows where things stand.** Without the worklog, "new conversation" means genuine amnesia and nobody would ever use it. With it, resetting a bloated three-week session is cheap and safe.
- **It answers cross-conversation questions.** If an agent has a CI conversation and an auth conversation, "what's the progress on the CI pipeline?" asked in the wrong one gets a confused answer. Topic-routing across conversations would be too clever to trust; durable notes the agent can read are reliable.
- It is human-readable outside the app and survives deliberate history clearing.

### TTS content comes from a `speak` tool, not the transcript

Each agent gets an in-process MCP tool (`createSdkMcpServer` + `tool()`) named `speak`, taking `{ message, priority }`. The agent decides what is worth saying aloud and when — including mid-task, without ending its turn. Tool inputs are never summarized, so the spoken line arrives verbatim, and the tool call renders in chat as an ordinary `tool_use` block (authentic Claude Code rendering).

Usage guidance lives in each agent's `AGENT.md`, not in code: call `speak` for questions, blockers, and completion; one sentence of plain prose; no paths or code; don't narrate routine steps.

**Prompt guidance is not enforcement.** The tool handler rate-limits `speak` per turn — an agent that narrates every step is as bad a failure as one that stays silent, and only the handler can prevent it. Overflow is refused *to the model* rather than dropped silently, so it can save its remaining budget instead of repeating into a void it cannot observe.

**`speak` is auto-approved and must stay that way.** It is namespaced `mcp__openroom-voice__speak`, and without an entry in `allowedTools` the permission flow prompts for it — stalling the whole turn behind a dialog asking permission to say a sentence aloud. It runs in-process and touches no file, network, or shell, so there is nothing to approve. There is a belt-and-braces short-circuit in `canUseTool` as well.

**Silence fallback:** if a turn completes (`SDKResultMessage`) and no `speak` fired, condense the final assistant text into one spoken line, so an agent finishing is always audible. Gated only on that agent having TTS enabled, the turn having succeeded, and the agent not having spoken for itself. The condense call goes through a tool-less `query()` with `model: 'claude-haiku-4-5'` — same subscription path as everything else.

**A result's `subtype` and `is_error` disagree, and the fallback must read both.** Measured on the bundled CLI: a model the account cannot use, and an OAuth token that expired and failed to refresh, both end the turn with `subtype: 'success'`, `is_error: true`, and the error sentence in `result`. The supervisor's error guard used to require a non-success subtype, so that shape fell through to the silence fallback, where "Failed to authenticate. OAuth session expired and failed to refresh." passed `speakableAsIs` (short, plain, no code) and was spoken as the agent's closing line while the chat showed the real reply. `turnOutcome` (`src/shared/turn-outcome.ts`) is now the one three-way decision (success, error, interrupted) that state, the queue, the failure text and the fallback all read; a flagged success is classified from its `result` text, and `classifyThrownError` learned "failed to authenticate" and "oauth", since "authenticate" is not "authentication". Result messages are never persisted, so this cannot be found in a transcript after the fact; it was reconstructed from the code and the measured payload.

**The condense turn runs on the same login as the reply it condenses, and reads the result the same way.** Field report from a WSL agent signed in only inside its distro: the chat showed the reply, and the voice said there had been an authentication error. `condenseForSpeech` always spawned the host binary, so the reply came from the distro's login and the summary from the signed-out host; and it checked `subtype` alone, so the auth failure's `success` + `is_error: true` shape passed and "Failed to authenticate…" was returned as the spoken line. The supervisor now hands it the agent's spawner (`spawnerFor`, the same one the session gets), and `condensedLine` reads the result through `turnOutcome`. Intermittent because only replies that fail `speakableAsIs` reach the model at all. `condense-result.test.ts` pins both against the measured payload.

**A reply that is already speakable skips the model entirely.** Condensing cannot be made fast: measured on the real path, a fresh `query()` costs 8–9 s of which only ~780 ms is CLI startup, and the floor is the round trip itself — a prompt as small as "Reply with the word ok." still took 6.3 s. A warm streaming-input session brings later calls to about 3.3 s, still an audible gap, and at the price of a resident `claude` subprocess that the concurrency cap exists to avoid. So `speakableAsIs` short-circuits: a reply under `MAX_SPOKEN_CHARS` with no code, markdown, links, paths or line breaks is spoken as written, in 0 ms. Measured in the app, an ordinary "how are you" reply went from ~9.6 s to 0 ms, while a reply carrying structure still condensed in 9.2 s.

The filter is biased on purpose. Rejecting speakable text costs one model call; accepting unspeakable text means hearing a file path read out character by character, so anything uncertain falls through to the model.

**A structured reply gives up its opening sentences before it pays for the model.** Field report: the working pip went out at the result and the voice arrived about fifteen seconds later. Measured on the day: the condense round trip was 6.6 s and 9.4 s, Kokoro then synthesises the whole line before any sound (0.65 s for a twenty-word line, 2.9 s for ten seconds of audio), and the PowerShell player is 0.27 s more. Most replies that fail `speakableAsIs` do so on a list or emphasis further down and open with a plain sentence, so `speakableLead` flattens the markup (`flattenMarkup`, shared with the side question's `speakableAnswer`), splits on a terminator followed by space (never on the terminator alone, or `condense.ts` leaves "ts now." behind as its own sentence), and takes sentences while each passes `speakableAsIs` on its own and the whole stays under `MAX_SPOKEN_CHARS`. The walk stops at the first sentence with code or a path in it, and an opening sentence that fails means the model still gets the reply, so the bias above is unchanged: a lead is spoken only when every sentence in it would have passed alone. The cost is hearing the reply's first sentence or two rather than a summary of it, a beat after the turn instead of nine seconds later. Streaming Kokoro by sentence (kokoro-js's `TextSplitterStream`; first chunk at 0.93 s against 2.9 s for the whole line, measured) and a resident player process were measured and left for later; note that `stream(string)` in kokoro-js 1.2.1 never closes its splitter, so it has to be driven explicitly.

**There is deliberately no duration gate.** One sat here at 30 s, reasoning that silence after a short turn is not confusing. Measured against real use, that was wrong in practice: an ordinary turn ("what files are in this directory?") runs about 6–10 s, and models routinely decline to call `speak` for work they do not judge to be a task — so agents finished in silence almost always, which reads as broken speech rather than as a considered default. A turn is a protocol boundary; its length says nothing about whether the work mattered.

`alreadySpoke` is what keeps the fallback rare in practice, and it is the gate that matters: an agent following its `AGENT.md` produces a better line than this can — mid-task, and written for the ear rather than condensed from prose. The fallback is a safety net under that, not a replacement for it. Note the cost it implies: every otherwise-silent turn now spends one extra Haiku call, and the condense round-trip means the line lands a beat after the turn ends, where an agent-authored `speak` is immediate.

**A prompt that arrived by voice is acknowledged aloud, and its opening line is echoed.** By text the user watches the reply stream in; by voice the pill turned and then nothing was heard for the two to eight seconds until the agent's first output, which with the window hidden is where voice started to feel unreliable. `VoiceController` passes `{ byVoice: true }` to `send()`, and `src/main/voice-ack.ts` holds the two decisions. At send time the app says its own line, "On it." or "Queued, after this task.", no model call, so it lands within about half a second on a system voice. Then the turn's opening assistant message is spoken if `speakableAsIs` passes it, the zero-millisecond check, and never condensed: that round trip is six to nine seconds, longer than the silence it would fill. "Opening" is decided by `openingCandidate`, and the first attempt got it wrong: with extended thinking the first assistant message of a turn is usually a thinking block on its own, and judging that one meant the real line was never considered. A thinking-only message is waited past; the first message carrying text offers it; one that opens with a tool call and no text ends the search with nothing to say. Measured through a probe in the dev app with a system voice: "On it." 156 ms after the prompt reached main, the agent's "I will list the files in this folder." at 3.0 s, and the finishing line a beat after; to a busy agent, "Queued, after this task." at 409 ms. Both go out at `progress` priority, so any question or blocker preempts them and the bus keeps only the latest per agent, which is what lets the agent's own opening line replace an unplayed "On it." rather than follow it. Gated on the agent's TTS being on in the supervisor, not left to the sink, because the sink's fallback for a voiceless agent is a notification and nobody asked for one. Neither line carries the agent's name, so the app's own audio can never form a wake phrase. Typed prompts stay silent. A voice turn that fails is told aloud too; see the `error` pip under the HUD. Rejected: asking the agent to acknowledge through `AGENT.md`, since there is no per-turn channel to tell it a prompt came by voice without altering the prompt, and an agent that says "on it" to typed prompts too is noise.

### One global SpeechBus

All speech is serialized through a single playback lane in main. Priority: `question > blocker > done > progress`.

- One utterance at a time; FIFO within a tier.
- Higher priority preempts lower mid-playback. Never the reverse.
- **Nothing is prepended to the spoken text — it is played verbatim.** The bus used to name the agent on a change of speaker, skipping it if the same one had spoken within 30s. In practice it meant hearing "Janet" read out before most lines, and it was buying identity information the agent's own voice already carries and the notification already puts in its title.
- **Expiry applies to `progress` only.** Keep just the latest `progress` per agent and drop progress older than 30s. `question`, `blocker`, and `done` never expire — an unheard question is the worst failure this app can produce.
- On burst (3+ simultaneous), speak the top-priority utterance and collapse the rest into one native notification.
- Barge-in: opening a capture (hotkey or mic button) stops playback and drops the queue. Detected speech does not; see "Barge-in is the capture opening" below.
- **Speech follows attention, not the input route.** `done` and `progress` are not played to someone looking at the pane they streamed into: `watching` (`src/shared/attention.ts`) is "main window focused and this agent selected", the same condition the HUD hides on, and `speechAllowed` holds those two tiers while it is true. `question` and `blocker` always play, since an unheard question is the worst outcome and a voice carries "I need you" in a way a row does not. The bus asks its gate at play time, never at enqueue, because a line can wait behind another agent's sentence while the user sits down or walks away; a refused line is dropped, notification included, since the pane already shows it. Whether the prompt was typed or spoken does not enter into it. `speakWhenWatching` in settings ("Speak even when I'm watching", off by default) is the opt-out. Unit-tested; not yet exercised live, since that needs a real TTS turn under focus.

Preemption and barge-in both require stopping audio mid-sentence, which constrains the TTS backend (see "TTS voices and models").

### Voice input: push-to-talk by default

Voice input ships **off**, and push-to-talk and wake words are **independent opt-ins** — each its own switch, neither requiring the other.

The reasoning is not just battery and OS mic indicators. An always-on mic is an unauthenticated control channel into a tool with Bash and file-write access — anyone within earshot, or a video playing nearby, can address an agent. Same code path either way; the default is what matters.

**Independent on purpose, and this was a reversal.** The wake switch used to require push-to-talk on, but the hierarchy existed only in the settings UI: main's `wakeAction` never read `voiceInputEnabled`, and the settings schema had already assigned the open-microphone argument to `wakeWordEnabled` alone. The coupling produced the worst state the app can be in — turn push-to-talk off with wake on and the wake listener kept the microphone open while its switch rendered greyed-out-and-checked. Wake's own opt-in, with its own warning copy, is the deliberate escalation; requiring push-to-talk first added a hoop, not consent, and made hands-free-only use impossible. `VoiceController.onTrigger` gates captures on *either* flag, because a wake match arrives through the same trigger as the hotkey — gating on the push-to-talk flag alone made wake-only mode hear its name and then refuse to listen.

**The tray's voice item is the panic switch, and off is total.** `trayVoiceToggle` (`src/main/tray-voice.ts`, tested): from any voice path on, one click turns *both* flags off and `refreshWake` runs so the microphone actually closes; from all-off, it restores push-to-talk only — silently re-arming an always-open microphone from a tray click would recreate the exact channel wake words make people opt into deliberately. The tray checkbox reflects `voiceActive` (either flag), as does the launch-time speech-model warm.

**Hotkeys are user-configurable**: a global "talk to the selected agent" binding, plus optional per-agent bindings that address one agent directly. Registration can fail when another app holds the combination — surface that in the UI rather than failing silently.

**The shortcut field commits when every key is let go, reads keys on the window, and pauses the app's own shortcuts.** Three field reports in one. Committing on the first key-down that made a valid accelerator ended the recording before the rest of the chord was pressed; `lib/chord-recorder.ts` (tested) builds the chord as keys go down, shows it, and commits on the last key-up. Escape closed the whole dialog, because Radix's dismiss listener sits on the document and runs before any handler on the field; the field now listens on `window` in the capture phase while recording, which runs first. And a combination already registered globally, the push-to-talk key itself, never reached the window and started a capture instead; `suspendHotkeys` releases them while a field records. Found by driving it: spreading a `KeyboardEvent` drops `shiftKey` and the other modifiers, which are prototype getters, so Ctrl+Shift+A saved as "A" while the plain-object tests passed. The reducer reads each flag, and a test with getters pins it.

**The composer's mic button is a third trigger route, and the discoverable one.** Hotkeys and wake words are invisible features; the mic beside the send button is where a new user learns voice exists. It calls the same `VoiceController.onTrigger` as a per-agent hotkey with this agent as the explicit target (so `captureTarget`'s ask-redirect never applies — clicking the mic in Juno's pane unambiguously means Juno), and the same click-again-to-stop toggle. With both voice flags off it opens Settings ringed on the push-to-talk switch instead of doing nothing; that gate is presentation only — main re-checks every precondition on trigger. The button's recording state comes from `voice:capture-changed`, a broadcast of `{phase, agentId}` to the main window piggybacked on the overlay-state send; it is deliberately not replayed on load, since a capture takes a click or a keypress and cannot predate the window.

**Voice input is gated on an installed speech model, and the switch is how the download is offered.** The setting can only become true with Whisper installed — a shortcut that exists but cannot possibly work is worse than no shortcut — but the switches themselves are *not* disabled while the model is missing. They were, with the download sitting at the bottom of the dialog, and the field report was a dead control whose explanation lived somewhere else: it read as broken. Flipping a switch without the model now offers the download in place (size, licence, local-only), declining cancels the enable — the setting is simply never written, so the switch never moves — and accepting downloads and then completes the toggle that asked. A failed download leaves the switch off with the failure shown beside it. The completion save reads the *latest* settings through a ref, not its closure: the download takes minutes and other settings can change during it. Registration failures are reported inline against the field that owns them — the settings dialog for the global binding, the agent editor for a per-agent one.

**Electron's `globalShortcut` fires on key-down only, with no key-up event**, so it cannot express true hold-to-talk on its own. It is therefore a toggle: press to start, press again to stop and send, and silence ends it on its own. Genuine hold-to-talk waits on the native key hook in the voice sidecar, where native modules are allowed.

**A capture ends three ways and only one of them dispatches.** Silence (an RMS endpointer against a noise floor sampled in the first 300 ms) and a second press both stop and send; Esc discards.

**The endpointer's cap is a stuck-microphone failsafe, not a UX bound, and its floor only ever ratchets down.** Three field failures from the first release shaped this, all one report: a long dictated prompt was cut off mid-sentence. `maxDurationMs` was 30s and fired unconditionally at the top of `push()`, then dispatched the truncated text with no indication anywhere — it is now 5 minutes (still unconditional, because the runaway case it guards, a TV keeping the detector loud, is exactly the one that never goes quiet), and the reducer marks a `maxDuration` end with a message the pill shows in any phase, since silently sending half an instruction to an agent with tool access is worse than the truncation. `hangMs` went 1.5s → 2.5s: a mid-prompt thinking pause read as "done", and toggle-to-talk makes the longer hang cheap — a second press still ends instantly. And the noise floor is the 25th percentile of the sample window rather than the mean, plus a downward-only ratchet against a 1s trailing window: talking during the 300 ms floor window used to set the threshold above the voice that set it and deafen the whole capture. Down-only is what keeps a genuinely noisy room adapted — its trailing window never goes quiet, so its floor never drops. A `MAX_FLOOR` clamp was considered and rejected: a loud room and a speech-polluted window are indistinguishable in 300 ms, and the clamp would have broken the noisy-room adaptation the tests pin. Esc is registered as a global shortcut for the life of a capture and released afterwards, because the overlay is `focusable: false` and can never receive a keypress itself — and holding Esc permanently would swallow it for every other application.

**The transcript is live: the capture streams to the sidecar and the pill shows the words settling while the user talks.** Apple's dictation rewrites earlier words as later ones arrive, and the app used to show nothing until Whisper had decoded the whole clip after the capture ended. Now the worklet posts a chunk every 300 ms (`stream` command, `WorkletMessage`), the overlay sends each on `overlay:chunk`, `VoiceController` feeds them to the sidecar's live session (`startLive` / `feedLive` / `finishLive` / `cancelLive` in `voice-rpc.ts`), and the sidecar answers with `partial` notifications, the first server-initiated message in the protocol (`isVoiceNotification`; the client's `onNotification`). `LiveSession` (`src/voice/live-session.ts`) decodes the open window whenever 0.7 s of new audio has arrived and no decode is in flight, so a slow machine gets fewer partials rather than a queue of stale ones; `LiveTranscript` (`live-transcript.ts`, pure, tested) applies LocalAgreement from Whisper Streaming (Macháček et al., 2023): a word is committed once two consecutive decodes agree on it at the same position, compared without case or punctuation so a comma settling later never uncommits a word, and the tail past the last agreement is shown dimmed as tentative. Past 12 s the window is cut at the quietest 300 ms older than 3 s (or at 10 s if nothing is quiet), the audio before the cut is decoded once more and sealed, and the buffer starts again, so the cost per decode stays bounded however long the dictation. `finish` waits for the decode in flight, decodes the open window one last time and returns sealed text plus that. The pill draws committed and tentative under the header, bottom-anchored so a long dictation shows its newest words. Measured through the built sidecar over stdio: partials every ~0.9 s, the final text 195 ms after the last chunk on a 5 s clip and 457 ms on a 42 s clip, and the 42 s clip complete and correct; and in the dev app with the overlay's `getUserMedia` replaced by a stream playing a WAV, the real capture, endpointer, pill and dispatch ran end to end. Two things seen and left: after a seal, the words just past the cut go tentative for one decode before firming again, and a sealed boundary once capitalised the next word ("Also, The").

**Moonshine is the speech model, chosen over Whisper and over a streaming transducer on measurement.** The question was how to get Apple-style live correction efficiently. Three synthetic clips (5, 13, 42 s) fed in 300 ms chunks on 2026-09-11: sherpa-onnx's streaming Zipformer (LibriSpeech) cost 15 ms per chunk with partials at 0.9 s but read "off package", "up date" and wrong tenses, in caps with no punctuation; NVIDIA's streaming FastConformer cost 22 ms per chunk, read better but still missed words, dropped the leading "Atlas" until fed 0.5 s of silence first, weighs 436 MB, and needs a punctuation model whose output was poor; Whisper tiny read every clip best but pads to 30 s, so a re-decode costs 280 to 860 ms whatever the audio length (38% of a core re-decoding once a second); Moonshine base matched Whisper's words with punctuation and casing at 55 ms per second of audio (27% of a core the same way, and bounded by the sliding window). Since the transducers lost on the thing that matters most for words sent to an agent with tool access, a few wrong words per hundred and no punctuation, the offline model with cheap re-decodes won. It runs on the transformers.js pipeline already in the sidecar, no native addon, and the words shown settling are the words sent. `STT_MODEL_ID` lives in the catalog so the sidecar and the settings dialog agree. Found on the way: the Whisper path truncated at 30 s with no error (84 of 118 words on a 42 s clip). Whisper was later removed and came back, tiny only, for wake segments, which the segmenter caps at 15 s (see "The speech model hears only the span Silero marked as speech").

**Every decision about a capture lives in one pure reducer** (`src/main/voice-input.ts`), with `VoiceController` executing the commands it returns. Audio is in a renderer and hotkeys are in Electron, so neither is testable where it lives; keeping the decisions apart from both is what makes them testable at all.

**The overlay window shows listening state.** When PTT fires, a bubble appears with the agent's name, identity colour, and target conversation title, moving through: listening (with a live waveform) → transcribing → dispatched. Voice input with no visible state is the failure mode that makes people distrust the whole feature — and showing the conversation is what stops a spoken message landing in a context the user didn't expect.

**The pill dismisses on its own timer; it never waits for the agent to speak.** The pill answers "did my words land where I meant", and that answer is complete at dispatch: it holds 1.4 s plus 40 ms a word, capped at 4 s, and goes. A `speaking` phase was declared in `OverlayPhase` and drawn by `pill.tsx` (arcs, a halo) and nothing ever entered it; it is gone. Tying the pill to speech was considered and rejected: it would hold for the two to eight seconds before the opening line, indefinitely for a queued prompt, and forever for an agent with TTS off or a turn that never produces a speakable opening. Continuity from the capture to the agent is the pip's job: the runtime goes `working` on dispatch, so the working pip is already on the HUD when the pill dismisses, and the `speaking` pip holds it there until the line has been heard.

**The same window doubles as a working HUD**, one pip per working agent, shown whenever the main window is unfocused or hidden. An agent blocked on a permission prompt appears there whether or not it is working and sorts first: with the window closed it is otherwise completely invisible. State is carried by rhythm rather than colour — colour already means "which agent", and at 9px a hue change reads as a different agent, not a different state. Hovering expands to a named roster; clicking a row raises the window on that agent.

**An agent with a line still to be heard stays on the HUD as `speaking`.** The pip was tied to the agent's state, and the state goes to `ready` at the result, so the dot vanished while the fallback was still condensing and the sidecar still synthesising: nothing on screen for the whole gap the paragraph above measures. Pending speech has two sources and `pipsFor` reads both: `AgentRuntime.speechPending`, which the supervisor sets around `speakFallback` and clears after the enqueue (after, so a HUD refresh between the two finds the line on the bus), and `SpeechBus.pendingAgents()`, agents with an utterance queued or playing, re-read on the bus's `onActivityChange`. `speaking` sorts last and any other state on the same agent outranks it, since a mid-task progress line is a detail of working. Its rhythm is the pill's vocabulary rather than the ring's: the working breath plus a soft disc in the agent's colour pulsing at the halo's 2100 ms cadence (`.or-pip-speaking`, opacity only); the roster reads "speaking". Reduced motion holds the disc steady. Unit-tested against both sources; not yet exercised live, since that needs a real TTS turn with the window unfocused.

**An agent whose turn failed stays on the HUD as `error`, and the failure is announced once.** Field report from the model-version 400 above: "On it.", a working pip, then the pip vanished and the room went quiet, which is exactly what a task finishing without a `speak` looks like. Nothing carried the failure out of the window: the silence fallback runs on success only, `pipsFor` dropped any agent that was not working or waiting, and no notification existed for an agent error at all (quota, updates and conversation deletion were the only ones). Three things now, each pure and tested. `pipsFor` keeps a runtime in `error` as an `error` pip carrying the message, sorted after a question (the roster can answer that) and before a quota pause (that clears itself), until the runtime leaves the state: the next prompt, Stop, End session, or the row click raising the window on that agent. Its rhythm is a stumble, two short beats then a long rest (`.or-pip-error`, `or-stumble`), because every other state's rhythm is regular and colour still means which agent; reduced motion gives it the slow breath held dim. `errorNotification` (`src/shared/error-notice.ts`) fires one native notification on the step into `error`, keyed on the previous state so the runtime re-emitted on every patch cannot repeat it, and main skips it while the user is `watching` that agent's pane, the same rule as speech. And a turn that came by voice is told aloud: `fail()` speaks `failureLine` (`voice-ack.ts`) at `blocker` when the session's turn was by voice, one plain constant per error kind and never the error text, which carries paths and exit codes; no agent name, as with "On it.". Measured with the built app against a scratch home and a missing workspace: the runtime went `error`, the overlay drew `or-pip or-pip-error` in the agent's colour with the roster reading the message, and Stop cleared it. The notification and the spoken line were not observed live: the first needs the window unwatched and the second a session-level failure on a voice turn, which a Max account does not produce on demand.

**The roster acts on `mouseup`, not `click`, and this is the only gesture that reaches it.** The overlay is `focusable: false`, and on Windows Chromium answers the `WM_MOUSEACTIVATE` for a window it cannot activate with `MA_NOACTIVATEANDEAT` — the press is discarded before the page sees it. Measured with a real cursor and a capture-phase recorder on the document: the row received `pointerup` and `mouseup` and nothing else, so no `click` was ever synthesised and an `onClick` handler never ran. It shipped that way in 0.1.0 and 0.1.1 because it had only ever been exercised with synthesised events, which deliver the whole sequence. Real input on this window means a real cursor (`SetCursorPos` + `mouse_event` from PowerShell) — a CDP `Input.dispatchMouseEvent` proves nothing here.

**The HUD answers, not just shows.** A permission prompt and a spoken question are both "an agent is waiting for you", and both used to need the main window raised. `pipsFor` now takes the pending `PermissionRequest[]` (`AgentSupervisor.pendingRequests()`) rather than a set of ids, and a `needs-attention` pip carries `permission: { id, summary, canRemember }`. The roster row renders the summary (`permissionSummary` in `permission-detail.ts`: the command as written, `Edit <path>`, else the tool's display name) and three `mouseup` buttons, Allow once / Allow for this session / Decline, which go through the same `session:permission-respond` channel as the pane, so main has one handler. Voice never answers a permission: anyone within earshot can address an agent, and approving Bash should need a hand on the machine. Measured with a real cursor in the dev app: the row showed `echo answered > answered.txt`, the click on Allow once resolved the prompt, the turn finished and the file landed in the worktree.

**"Allow for this session" returns only the CLI's suggested rules, re-addressed to the session.** The CLI answers a prompt with the full set of updates it would apply for "don't ask again", and the handler used to return that set verbatim. Measured against the bundled CLI on `touch same.txt`: three updates, the rule `Bash(touch same.txt)` bound for `localSettings`, an `addDirectories` grant, and `setMode: acceptEdits`. Returned as-is, one click on a Bash prompt silently put the session into accept-edits mode, and wrote both the rule and `defaultMode: acceptEdits` into the workspace's `.claude/settings.local.json`, a file agents never read (`settingSources: []`) but terminal Claude Code in that repository does. `sessionScoped` (`src/shared/permission-scope.ts`) keeps the `addRules` entries and sets `destination: 'session'`. Measured with a rule-only session update: the identical command no longer prompts, a different file does, a `Write` still does, and the init keeps reporting `permissionMode: default`. Two CLI facts found on the way: plain `echo`, `ls`, `cat` and the rest of the read-only list never reach `canUseTool` at all, so they cannot exercise a permission flow; and a command with a redirect (`echo x > f`) prompted every time even with an exact rule, so use `touch` or `mkdir` to test one.

**A spoken question becomes runtime state, and push-to-talk aims at it.** The SDK records nothing when an agent asks: the turn is a `success` like any other and the agent reports `ready`. `recordAsk` in the `speak` handler notes a `question` or `blocker` on `TurnSpeechState.asked`, and when that turn ends normally the supervisor patches `AgentRuntime.awaiting = { text, since }` (`awaitingAfterTurn`, `src/shared/awaiting.ts`); an error or an interrupt records nothing, and any prompt sent to the agent by any route clears it, as does `stop()`. The HUD shows it as an `asking` pip, sorted after permission prompts and before quota pauses, with the question text on the roster row. `captureTarget` then redirects the *global* hotkey to the most recently asking agent ahead of the selected one; a per-agent hotkey or wake phrase still wins. The pill names the target and its conversation before any audio is captured, so the redirect is visible and Esc discards it. Measured: with Juno selected and Atlas waiting, the hotkey opened a pill for Atlas on Atlas's conversation. Inferring the question from the assistant text was rejected (a heuristic whose wrong answers are silent), as was a separate `ask` tool (`speak` with `question` already means this, and every AGENT.md would change).

**The bubble keeps room under it for its own shadow, and a refusal with no agent is one line.** The overlay is a fixed transparent rectangle, and the pill sat 12 px from its bottom edge with a shadow that reaches 40 px below the box, so the shadow was cut off in a hard line; the container's bottom padding is 48 px now. A refusal raised before any agent was chosen ("Voice input is turned off", "No speech model installed") used to render an empty header, a grey dot beside nothing, with the message on a second line; `bareError` in `pill.tsx` puts the message where the name would be.

**The overlay re-places itself on every show and every display change.** Its bounds used to be computed once, in `create()`, from whichever display was primary at launch; the field report was the pill turning up on the other monitor. Displays come and go after launch — a DisplayPort monitor sleeping, a dock, a re-ordered arrangement — and Windows 10 moves windows off a display that vanishes without moving them back, hidden windows included. `place()` recomputes from `screen.getPrimaryDisplay()` and calls `setBounds` only when the position differs, on `display-added`/`display-removed`/`display-metrics-changed` and just before `showInactive()`. Still the primary display by choice — one predictable place — and `overlay-window.test.ts` pins both the re-placement and the no-churn case.

**The overlay can be dragged, and goes back where it was left.** Resting the pointer on the pill or the HUD roster for three seconds (`useGripVisible`, `use-grip.ts`) shows a grip; dragging it moves the whole window, and main saves the drop point to `<OPEN_ROOM_HOME>/overlay.json`. `overlayPosition` (`src/shared/overlay-position.ts`, tested) is what `place()` uses on launch, on every show and on every display change: the saved spot while the content at the window's bottom is on some display, the bottom-centre default otherwise, with the saved value kept so the pill returns when that monitor does. The drag is run by the page, not the OS. `app-region: drag` did nothing here: driven with a real cursor through `mouse_event`, the grip showed and the window never moved, because this window swallows its mouse-down and the OS drag starts on one. So main makes the window focusable only while the grip shows (`setGrip`, after a deliberate three-second rest), the grip captures the pointer on press and sends screen positions (`overlay:drag`), and main moves the window by the distance since the press, saves on release, and blurs the window to hand focus back. Measured: a 600 by 500 pixel drag moved the window exactly that far, the position survived a restart, and a click on the pill's new cancel button (`cancelRequested`, the same event as Esc) closed a live capture in under a second. The pill takes clicks now (`useHitBox(true)`); it used to pass them through so nothing reaching past it could hit it by accident, and being able to drag it out of the way is the trade.

### Wake words are dynamic by construction

**Two gates, not one.** An RMS segmenter in the overlay decides which slices of an always-open microphone are worth sending anywhere; Silero VAD in the sidecar decides whether a slice is speech; only then does Whisper run. The order matters — measured, Silero costs 0.15 ms per 32 ms frame and Whisper costs hundreds of milliseconds per segment, so the cheap gate has to come first. A loud 220 Hz tone scores 0.07 on Silero: exactly the music, typing and fan noise an amplitude gate would have passed straight to Whisper.

**Silero's verdict is a duration, not a proportion.** The segmenter pads every utterance by design — 500 ms of pre-roll so the onset survives, 700 ms of hang before the segment closes, and whatever silence has accumulated since the last idle flush — so the same phrase scores differently depending only on how quiet the room was beforehand. Measured, "Hey Derek" carries ~650 ms of voiced audio: 0.435 as a ratio in isolation, but 0.174 in the segment the app actually cut, which put it under a 0.25 ratio bar and dropped every wake word on the floor. `acceptsSpeech` asks for 250 ms of speech instead, which is independent of the padding around it.

**The speech model hears only the span Silero marked as speech.** Moonshine returns an empty transcript for audio that opens with silence, and every wake segment does (the pre-roll plus whatever quiet built up since the last idle flush). Nobody re-measured wake words when Moonshine replaced Whisper, and the field report was "horrible". Measured on 126 synthesised "hey <name>" clips (6 names, 3 phrasings, 8 voices) through the real VAD, model and matcher: 82 matched with 0.5 s of silence before them and 0 with 3 s. `speechSpan` in `vad.ts` cuts the segment to the first and last speech frame plus 250 ms and 300 ms of margin, and the same sets then scored 121 and 118. Whisper tiny scored 125 to 126 with or without the cut, heard names Moonshine misheard ("Hey derek" for Eric), and did better in noise (115 against 108 of 126 at 15 dB), at about 330 ms a segment against Moonshine's 110 ms, paid only when someone talks. So wake segments go to Whisper tiny when it is installed (`WAKE_MODEL_ID`, beside `STT_MODEL_ID`; `stt.ts` keeps one pipeline per id) and to Moonshine otherwise, decided per segment in the sidecar. Main still gates wake listening on Moonshine alone, so an install from before Whisper came back keeps working; the settings dialog offers both models when the wake switch is flipped (405 MB together) and lists each with its own download. Measured in the dev app against an empty models folder: the offer named both, "Download and enable" fetched them in turn and the switch came on. The matcher also accepts `hi` and the prefix run into the name ("Hanova"), which Moonshine writes often in noise (`unfuse` in `wake.ts`, guarded so "hello" never wakes an agent called Ella). And the segmenter's noise floor is the 25th percentile of the last 6 s rather than the mean of the first 400 ms, fixed forever: a room that got louder held segments open to their 15 s cap, so the wake phrase landed mid-segment where the anchored matcher could not see it. The segmenter change is tested but was not measured on real audio.

**Dictation had the same silence bug, worse.** `LiveSession` decodes through `transcribeSpeech` in the sidecar, which cuts each window to Silero's speech span when Silero is loaded. Before: a pause of 1 s after pressing the hotkey returned an empty transcript for 5 of 6 clips, 2 s for all 6, and a 31 s dictation with 2 s pauses between sentences kept only its last sentence. After: all complete. Silero used to be fetched only for wake words; `startLive` now fetches and loads it (2 MB) in the background, so a first dictation without it goes through untrimmed rather than waiting.

**Real wake segments can be recorded by creating `<OPEN_ROOM_HOME>/wake-debug/`.** `wake-debug.ts` then writes each segment the sidecar receives as a 16 kHz WAV beside a line of `log.jsonl` (speech milliseconds, transcript). Off otherwise, so no one's voice reaches the disk unless they made the folder, and it works in an installed build with no flag. The synthetic clips above are clean TTS; this is how a report of misses from a real microphone gets measured.

**Always-on listening costs roughly 8% of one core** — measured across alternating runs as 7.5–9.1% with wake words on against a 2.9–8.8% baseline, or about 0.7% of a 12-core machine. The run-to-run spread is wider than the delta, so treat it as an order of magnitude and not a figure. Whisper never runs in a quiet room; the idle path is one RMS per animation frame and a discarded buffer every three seconds.

An earlier note here claimed 1.9%. That was measured while the overlay's poll loop was silently dead (see the `backgroundThrottling` gotcha), so it was measuring a listener that never ran. Most of the real cost is a 60 Hz render loop kept alive in a hidden window; driving the gate from the AudioWorklet instead, which is never throttled, would remove it.

**`deviceId` must be constrained with `exact`, not `ideal`.** Counter-intuitive and measured: Chromium treats an `ideal` deviceId as a soft preference and quietly keeps using the system default, so a selected microphone appears to be ignored while `getUserMedia` reports success. `exact` genuinely selects, and throws `OverconstrainedError` once the device is unplugged — which is what the fallback to an unconstrained open is for. Machines routinely have three inputs and the default is frequently not the one being spoken into.

**The settings meter is the only path that opens the microphone without voice input being enabled**, which is why it is bound to a button press rather than to the dialog being on screen, and why main stops it after 20 s regardless. A settings panel that silently lit the OS microphone indicator would undercut the whole reason voice input ships off. Levels arriving after the test has stopped are dropped in main rather than drawn — the overlay's stream takes a moment to close, and a bar still moving after "stop" says the microphone is open when it is not.

**Two concurrent `getUserMedia` streams on one device work** — measured with wake listening and the meter open together, both reading real audio (0.329 and 0.185 on the same utterance). So the meter opens its own stream rather than borrowing the wake listener's, which matters because the case it exists for is the one where nothing else has the microphone open at all.

**The microphone setting stores the device's label, never its `deviceId`.** Measured on the packaged app across two consecutive launches with nothing changed: the Razer's id went `534c5220…` → `b423ca3c…`. Chromium salts `deviceId` per origin, and the overlay is a `file://` page whose origin is opaque, so the salt is fresh every launch. A stored id therefore matched nothing after a restart — the settings `Select` painted blank (an orphaned value looks like "nothing chosen", hiding "System default" too) and capture silently fell back to the default. `resolveMicrophone` turns the stored label into this session's id at the moment a stream is opened, and the dialog keeps an unplugged selection visible as "(not connected)" rather than blank.

**A selected device only applies to the next stream opened, never to a running one.** `overlay.setMicrophone` sets a static the next `getUserMedia` reads. So changing the microphone has to restart anything already listening — `refreshWake` tracks `lastMicrophoneId` and stops the listener on a change, and `Meter` compares against the id it opened on and reopens. Without both, the meter would reopen on the new device and report it healthy while the wake listener carried on hearing the old one: a confident, wrong answer to the exact question the meter is there to settle.

**Meter levels are logarithmic, and that is not cosmetic.** Speech RMS runs about 0.05–0.3 against a full scale of 1, so a linear bar leaves a working microphone twitching in its bottom third and reads as broken. `meterLevel` maps −60 dB…−6 dB onto the bar, and `meterVerdict` answers the actual question ("is this the right device") from the peak rather than the current level — sticky once heard, since the pause between two words is not evidence of a dead microphone.

**Device labels are only visible to a page holding microphone permission**, which is the overlay and nothing else. It enumerates and reports upward; the settings dialog reads a cache in main and subscribes to changes, because enumerating there would return the right number of devices with blank names. No `getUserMedia` call is needed to unlock the labels — the permission grant alone is enough.

**Segments keep 500 ms of pre-roll.** The gate opens on the first loud frame, which is already partway into the first word. The worklet retains a tail when discarding so the onset survives.


Agent names are user-defined at runtime, so trained-keyword engines (Porcupine et al.) don't fit — there is no runtime API to mint a keyword for an arbitrary typed name. Instead: always-on VAD gates a tiny local Whisper model; the leading words of each transcript are fuzzy-matched against the agent-name list. Any name works instantly with no training.

**Self-trigger prevention, in three layers.** The wake phrase requires a `hey` prefix (`hey atlas`), and the SpeechBus emits no agent name at all, so TTS output cannot form a valid wake phrase *by construction* — a proof rather than a heuristic, tested against the exact string the bus produces. This used to rest on the bus emitting a bare `Atlas —` prefix that the `hey` requirement neutralised; dropping the prefix strengthened it rather than weakening it, since there is now no name in the audio to begin with. The `hey` requirement still matters independently: a name can reach the microphone by other routes. Behind it, listening is muted for the duration of playback plus 300 ms, and any transcript that overlaps the currently-playing text by 60% is dropped as an echo.

**A wake prompt to a busy agent is queued, and the pill says so.** "Hey Atlas, run the tests" while Atlas is mid-turn never interrupts (a voice is an unauthenticated channel); the supervisor queues it behind the running turn, which is right, but it used to be invisible: the inline-prompt route went straight to the supervisor with no pill at all, and the capture route showed the dispatched tick, so a prompt waiting behind a two-minute task read as delivered. `send()` now says `queued: true`, the wake controller hands both routes to `VoiceController` (`onSpoken` for a prompt heard whole, the reducer's `spoken` event), and the pill's dispatched bubble carries "Queued behind the current task" and holds two seconds longer. Measured through a file probe in the dev app: the pill read the prompt with the queued line while the runtime listed it in `queued`.

**"Hey Atlas, by the way, ..." is a side question: answered now, from the conversation, and kept out of it.** The CLI's `/btw` ("Ask a quick side question without interrupting the main conversation") is a terminal-UI command dispatched as a control request, so it cannot be passed through the streaming input; this is built instead. The marker is its own phrase, not the busy-state reading of the plain wake phrase, because "also update the README" and "what's the status" sound identical to busy-state and guessing wrong is bad both ways: an instruction answered as a throwaway is silently dropped from the task, and a question queued as an instruction is asked of the agent two minutes later as work. `matchWake` strips a leading `by the way` / `btw` / `quick question` / `side question` after the name (lexical, since a phonetic match would let "buy the weigh" through) and sets `aside`; the bare marker opens a side-question capture. `SideQuestions` (`src/main/side-question.ts`) runs a forked, unpersisted, tool-less, single-turn `query()` on the active conversation (`resume` + `forkSession: true` + `persistSession: false`), so it reads the context without appending to it and can run while the main turn is still going, since it is a separate process. Measured: 5.2 s to a correct "you asked me to count to 3000" against a live conversation, and no session file written. `persistSession: false` is load-bearing there: a persisted fork copies the parent's history *with its `open-room:<agent>` tag*, so it would appear in the conversation switcher as a duplicate of the conversation it forked from (measured: 73 tag lines in the fork file). The answer goes to the speech bus at `question` priority, since the user asked and is waiting, and onto `AgentRuntime.aside` for a card above the composer labelled "not part of the conversation", cleared by the next prompt or its X; the pill shows "Side question", the question, "Asking…", then the answer, held for its length. `speakableAnswer` flattens markup and keeps the leading sentences under `MAX_SPOKEN_CHARS`. Not available for WSL agents yet (the fork would need the distro's spawner). Verified in the dev app during a running turn: pill, runtime, card and dismiss all as described; the main turn stayed `working` throughout.

**Barge-in is the capture opening, not detected speech.** It used to be detected: while muted the wake listener kept its segmenter running and called barge-in on any speech onset, on the reasoning that `echoCancellation: true` subtracted the app's own voice. It does not. Chromium's echo canceller only has the audio Chromium itself plays as a reference, and TTS plays through a separate PowerShell or `afplay` process, so on speakers the app's own voice read as someone talking over it. Field report: agents' speech cut out mid-sentence, sometimes, with wake words on and a desk microphone; loud syllables crossed the segmenter's threshold. The muted listener now only keeps its noise floor current, and `startCapture` in main calls `speech.bargeIn()` before the overlay opens the microphone, which also keeps the tail of a line out of the capture. Talking over an agent without a hotkey or a wake phrase no longer stops it; making that work again means playing TTS through Chromium so the canceller can see it.

**Name collisions are phonetic, not lexical.** Matching happens against Whisper transcripts, so validate with a phonetic key (double metaphone), not edit distance — `Sky`/`Skye` are edit distance 1 and acoustically identical, while `Atlas`/`Atlas-2` are edit distance 2 and also identical once spoken. Warn additionally on single-syllable names and names that are common English words (`Scout`, `Ready`), which misfire constantly in open transcription.

## Agent configuration

Stored at `~/.open-room/agents/<id>/` — `config.json` plus `AGENT.md`. Both are plain files, editable outside the app. `OPEN_ROOM_HOME` relocates the root, which is how tests drive the app without touching a real home directory.

**`id` and `name` are separate on purpose.** `id` is the slugified directory name, fixed at creation; `name` is the display and wake-word label and can change freely. Renaming therefore never moves a directory or orphans an agent's sessions. The slug is lowercased because Windows and macOS default to case-insensitive filesystems, so `Atlas` and `atlas` would otherwise collide as directories. `ConfigStore` treats the directory name as authoritative and rejects a `config.json` whose `id` disagrees with it.

**Deleting an agent ends its session first.** The delete handler used to be `rm -rf` on the directory and nothing else. Measured: deleting an agent mid-turn returned in 2 ms, its CLI subprocess kept running the turn, and its runtime stayed listed as `working` for an agent nothing could open. `AgentSupervisor.forget` stops the session (through the same `stop()`, so a running turn is interrupted rather than waited for) and drops the runtime and the conversation choice; the handler calls it before the store deletes the directory. Measured after: 273 ms, no runtime, no process.

```ts
type AgentConfig = {
  id: string // slug + directory name; stable across renames
  name: string // wake-word target, freely renameable
  color: string // identity color, used in overlay + chat
  avatar: 'clawd' | 'bit' | 'terminal' | 'block' | 'loop' // pixel character, drawn in `color`
  model: string // any `claude-*` id (MODEL_ID); MODELS names the known ones
  effort?: 'low' | 'medium' | 'high' | 'xhigh' | 'max'
  fallbackModel?: string
  workspacePath: string
  mcpServers: Record<string, McpServerConfig>

  // Permissions — see note below; these are not equivalent
  permissionMode: 'default' | 'plan' // never 'bypassPermissions' from the UI
  allowedTools: string[] // auto-approve, no prompt
  disallowedTools: string[] // hard deny, supports scoping e.g. "Bash(rm *)"

  persistSession: boolean // false = ephemeral; no conversation history, no resume
  hotkey?: string // optional per-agent push-to-talk binding
  tts: { enabled: true; voice: VoiceRef; rate: number } | { enabled: false }
}

type VoiceRef =
  | { provider: 'system'; id: string } // OS voice identifier
  | { provider: 'piper'; id: string } // model filename in ~/.open-room/voices/
```

**`allowedTools` is an auto-approval list, not a sandbox.** Omitting a tool means "prompt for it," not "block it." A UI checkbox group labeled _allowed tools_ reads to users as _unchecked = blocked_, which is wrong and dangerous. Model both lists explicitly, label them accurately, default to prompting, and never expose `bypassPermissions` in the UI — least of all for voice-initiated prompts, where the requester may not be the person watching the screen.

The editor therefore renders **one three-state control per tool** — *Ask every time* / *Always allow* / *Never allow* — under the heading "Every tool is available to the agent. This controls whether it asks you first." Two checkbox lists cannot express the three real states without implying a fourth that does not exist. `toolPermissionOf` resolves a config that lists a tool in both arrays to `deny`, since the restrictive reading is the safe one.

**An agent is told its name in code, not in the role file.** The preset introduces the model as Claude Code and AGENT.md is the user's, so nothing said "you are Janet"; asked its name, an agent answered "Claude". `identityPreamble` in `agent-options.ts` prepends one paragraph to the appended context at every spawn, built from `config.name`, because the name is renameable and a line written into the template would go stale on the first rename. It says the agent is still Claude Code underneath, so "what runs you" stays honest. Pinned in `agent-options.test.ts`, rename included.

**Agents run with `settingSources: []`, and this is load-bearing.** The options are built by `agentQueryOptions` in `src/main/agent-options.ts`, kept pure and separate from `AgentSupervisor` precisely so this can be asserted on — every invariant it holds fails silently, since an agent with the wrong tool access or the wrong credentials still runs and still answers. `agent-options.test.ts` pins the ones that matter. Omitting the option makes the SDK load user, project and local settings, which means the machine decides what an agent can do rather than its config. Measured on one developer's install before the change: an agent configured with `allowedTools: ["Read","Glob","Grep"]` was handed **73 tools, 8 MCP servers and 102 slash commands** — Figma, Supabase, Playwright, GitHub and a claude.ai Google Drive connector among them, four of those servers coming from `enabledPlugins` in `~/.claude/settings.json`. With `settingSources: []` the same agent sees roughly **32-35 tools, 1-2 MCP servers and 46-47 slash commands**.

Two reasons it matters beyond tidiness. The agent editor tells the user "Every tool is available to the agent. This controls whether it asks you first" — which was true of a tool list they had never seen and could not edit. And the same agent config behaved differently on a different machine, which for an app installed from source is a real divergence from "each agent has its own model, tool/MCP access". An agent that genuinely needs a server gets it through its own `mcpServers`, which is merged on top.

It is also a large latency win, because each of those servers is started per turn: a trivial turn went from 6.0–8.1 s to about 2.0 s. Several were `pending`, `failed` or `needs-auth` on every spawn.

### Fable is offered, and the account's plan decides whether it is enabled

`MODELS` lists Fable 5.1 and Fable 5. Fable is the first tier a subscription may not include, and the SDK does not say so up front: an agent configured for it starts, reports an init, and only then ends the turn with an assistant message `error: "model_not_found"` (measured on a bogus id: `model: "<synthetic>"`, text "There's an issue with the selected model (X). It may not exist or you may not have access to it.", and a result that says `success`). That code used to map to `unknown`; it is now `model-unavailable` with a hint that points at the agent settings.

**The bundled CLI knows the answer before any turn.** `supportedModels()` on a live session lists the picker the account gets, and an account with the Fable tier has a Fable row. Reading it needs an init, and an init needs a first message; a query whose generator never yields sits there forever (measured, 30 s). A local slash command is the cheapest first message there is: `/context` runs inside the CLI with no model turn, so the whole probe (`src/main/model-access.ts`) is one spawn, measured at 2.2 s and zero tokens. It runs after the login check says signed-in and on each recheck, and lands as account state beside login and quota (`getModelAccess`, `models:changed`).

**The list is a picker, not a catalogue.** Two runs on one Max account listed `claude-fable-5-1[1m]` once and `claude-fable-5[1m]` once, and Fable 5 ran while only 5.1 was listed. So `modelAllowed` (`src/shared/model-access.ts`) answers "does the account have the Fable tier" and never "is this exact id listed": a non-Fable id is always allowed, a Fable id is refused only when access is `known` and no Fable row appeared, and `unknown` allows everything, because a probe that failed must never lock a model the account does have.

**Disabled, not hidden.** A Fable row that vanished would read as the app lacking the model rather than the plan; the editor and the session controls show it disabled with "Not included in your plan", and an agent already configured for one carries an amber line in its pane header. The plan-lacks-Fable branch could not be exercised on this machine (Max account) and is tested against a stubbed list; the runtime backstop is tested against the measured payload.

**The picker follows the bundled CLI, so a new model needs no Open Room release unless it needs a newer CLI.** The same probe's rows are aliases (`sonnet`, `opus[1m]`, `default`) that resolve to wire ids, sometimes dated (`claude-haiku-4-5-20251001`); `discoveredModels` keeps the ones `MODELS` does not name, labelled from the description, which leads with the real name ("Opus 5 with 1M context · Best for everyday, complex tasks", measured; the display name is only "Opus"). `pickerModels` puts those first, then `MODELS`, plus the agent's own model if neither names it, so a model found on an earlier launch still shows while this launch's probe is unknown. The config schema and `sanitizeOverrides` check a model id's shape (`MODEL_ID`, `claude-` then lowercase, digits, dots and dashes) rather than membership of a list. `MODELS` stays as curated labels and the offline fallback. Measured in the dev app with Sonnet 5 taken out of `MODELS`: the probe reported it and the editor offered "Sonnet 5 — Efficient for routine tasks" first. The limit is the gotcha below: the list is whatever the bundled CLI knows, and a model that needs a newer CLI still needs an SDK bump and a release.

**The plugin servers go; the claude.ai connector does not, and the two runs that established this disagreed.** The docs say `~/.claude.json`, claude.ai MCP connectors and managed policy settings are read regardless of `settingSources`. The first measurement appeared to refute that — the only server left was `openroom-voice`, and this file recorded "trust the init message over the documentation". A later run on the same machine reported `["claude.ai Google Drive", "openroom-voice"]`, which is what the docs predicted all along.

So the honest reading is narrower than either run alone: the four `enabledPlugins` servers reliably go, `context7` and `magic` were absent from both runs, and the Google Drive connector's presence depends on account-side state neither run controlled. Do not treat the server count as deterministic. **Read it off the init message at the time it matters** — that instruction survives; what did not was concluding the docs were wrong from a single sample.

### An agent can run inside a WSL distro

Opt-in per agent (`wsl: { distro: string } | null`, default null): when set, `workspacePath` is a Linux path and the agent's `claude`, `git`, and file listing all run inside that distro instead of on Windows. Windows-only, the editor's "Run in WSL" control only renders when `getAppInfo().platform === 'win32'`.

**The SDK is unchanged; `spawnClaudeCodeProcess` is the only difference.** A WSL agent still goes through the same `query()` call, the same streaming generator, the same `Options` shape as a host agent. `agentQueryOptions`'s custom-spawner argument, added for this, is `WslRuntime.spawnClaude(distro)` in place of the SDK's own subprocess launch: same stdio JSON-RPC protocol, different process (`wsl.exe` instead of the bundled `claude.exe`). Nothing about message handling, permission prompts, or session lifecycle in `AgentSupervisor` needed to know the difference. That was the point of taking the spawner as an injected argument rather than branching supervisor logic on `agent.config.wsl`.

**The argv shape, and why each piece is there.** `wslClaudeArgv` (`src/shared/wsl.ts`) builds `-d <distro> --cd <cwd> --exec /usr/bin/env <K=V...> bash -lc 'exec claude "$@"' claude <args...>`:
- `--exec`, never a default shell, so `wsl.exe` never re-parses or re-quotes the command line itself. That is the risk `wslClaudeArgv`'s own comment calls out, since `wsl.exe` re-escapes whatever shell it launches.
- `bash -lc 'exec claude "$@"'` is a fixed script with every real argument positional after it, for the same reason the PowerShell TTS scripts are fixed constants: a script that never varies is one AMSI-class rescan, not one per turn. (That reasoning is Windows-only here; `bash -lc` invokes a login shell purely to pick up a version manager's PATH entries, not for any scan-avoidance.) `-l` matters because a distro with `claude` installed via nvm or similar puts it on a PATH only a login shell sources.
- `/usr/bin/env K=V...` in front carries the CLI's own environment across explicitly rather than relying on WSLENV, which requires each variable to be registered and translated by name.
- `wslChildEnv` allow-lists `CLAUDE_*`/`ANTHROPIC_*` keys and still blocks `ANTHROPIC_API_KEY` (same reason as the host), plus `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` (Windows paths, meaningless inside the distro). Nothing else from the Windows environment crosses. `Path`, `USERPROFILE`, `TEMP` would all point at the wrong OS; the login shell supplies the Linux equivalents.

**Sessions read through a worker with a different `CLAUDE_CONFIG_DIR`, because main's own is process-wide.** The SDK's session functions (`listSessions`, `getSessionMessages`, `renameSession`, `tagSession`, `deleteSession`) read `CLAUDE_CONFIG_DIR` from `process.env` at call time, live. Main runs every agent's session calls in one process, so setting it there for a WSL agent would misdirect every other agent's session read for as long as it was set. `SessionReader` (`src/main/session-reader.ts`) instead spawns one small worker per WSL distro (`process.execPath` + `ELECTRON_RUN_AS_NODE=1`, same shape as the voice sidecar) with `CLAUDE_CONFIG_DIR` fixed to the distro's own `~/.claude`, read as a `\\wsl.localhost\<distro>\...` UNC path. Measured: the SDK finds a session under a mixed-case slug that way and reads its messages. Requests cross on one JSON-RPC line per call over stdio (`src/shared/session-rpc.ts`), the same wire shape as the voice sidecar's protocol. `ConversationStore` picks `hostSessions` (the SDK called directly) or a `SessionReader` per agent, so host agents pay none of this.

**`gitFor`, `find`, and the editor all resolve inside the distro too.** `gitFor(agent)` (`src/main/ipc.ts`) returns `new Git(wsl.git(distro))` for a WSL agent, a `GitRunner` that runs every git command through `wslExecArgv`, so the diff view, `inspectWorkspace`'s repo check, and worktree probing all see the distro's git, not a Windows one that may not exist there (this machine's `docker-desktop` distro has none, see below). The `@` picker's file list runs `find . ( -name node_modules -o -name .git ... ) -prune -o -type f -print` inside the distro (`WslRuntime.listFiles`) rather than walking `\\wsl.localhost\...` from Windows, which would be a cross-network directory walk for the same result `find` gets natively. Open-in-editor resolves the target as `linuxToUnc(distro, path)`, `\\wsl.localhost\<distro>\<path with / turned to \>`, so the configured editor opens the file over the same network share Explorer would use to browse the distro.

**Worktrees are deliberately unsupported for a WSL agent in this phase.** `wslPlacement` always returns `{ cwd: workspacePath, isolation: { kind: 'workspace' } }` unless the agent's config has `worktrees: true`, in which case it returns `{ kind: 'fallback', reason: WSL_WORKTREE_REASON }`, the same visible-fallback pattern as a plain non-git workspace, never a silent no-op. The editor disables the worktree switch outright when a distro is selected (`disabled={Boolean(wslDistro)}`) with an inline "Not available for WSL agents yet." rather than letting it be turned on and then explained away in the header.

**The distro has its own Claude Code login, separate from the host's.** `checkLogin(distro)` runs `claude auth status --json` inside the distro through the same `bash -lc` shape, parsed with the host's own `parseAuthStatus`. `wslLoginHint(distro)` names the two commands directly (`wsl -d <distro>`, then `claude`) rather than pointing at the host's first-run screen, which would send someone to sign in on the wrong side of the boundary.

**Verified against a real distro.** This machine has only `docker-desktop`: no `bash` login profile worth anything, no `git`, no Claude Code (see plan.md Phase 10 for the full record). The editor's distro list showed `docker-desktop`; selecting it swapped the workspace field's description to the Linux-path text, disabled the worktree switch with its note, and a Windows path (`C:\Users\Lincoln`) failed validation with "Use a Linux path inside the distro, like /home/you/project"; `/tmp` cleared the error. `inspectWorkspace('/tmp', { distro: 'docker-desktop' })` returned `{ exists: true, git: false }`; `inspectWorkspace('/nope', ...)` returned `{ exists: false, git: false }`. Setting the workspace to `/nope` and sending a prompt failed with the pane showing exactly `Workspace folder not found in docker-desktop: /nope` (`error.kind: 'workspace-missing'`). With the workspace back at `/tmp`, sending a real prompt to `docker-desktop` (which has no `bash`, so `claude` never runs) failed visibly rather than hanging: `listRuntimes()` reported `state: 'error'`, `error.kind: 'crashed'`, `error.message: 'Claude Code process exited with code 127'` (127 is the shell's own "command not found"), 1.3 seconds after the prompt was sent, well inside the "stuck starting" failure mode this was checked against. `listWorkspaceFiles('tux')` ran the `find` path successfully and returned real filenames from the distro's `/tmp`. The header read `WSL · docker-desktop`.

**Not measured on this machine, needs a distro with Claude Code installed and signed in, and a git repository at a Linux path inside it:** a real turn's output and spawn timing on a cold vs. a warm distro (brief Step 3); the files-changed row, its diff, and the editor opening a `\\wsl.localhost\...` path after a real `Write` (Step 4); session resume across a stop/resend and an app restart, and the conversation switcher's rename/delete reflected via `wsl -d <distro> ls ~/.claude/projects/<slug>/` (Step 6); the sign-out hint's exact wording as shown in the pane after `claude auth logout` inside the distro; and Stop/Interrupt timing for how quickly the `wsl.exe` child exits. See plan.md Phase 10 for the exact commands the next run needs.

### MCP server health comes from the init message, with detail on demand

Every init message — re-sent each turn — carries `mcp_servers: { name, status }[]`, and it used to be discarded: on one developer's install a plugin server was `failed` on every spawn with nothing shown anywhere. `src/shared/mcp-health.ts` holds the decisions; `McpHealth` in the pane header draws them; the supervisor executes.

**The per-turn statuses are free; the error text is not.** `mcpHealthUpdate` folds each init's statuses into `AgentRuntime.mcpServers` and asks for `query.mcpServerStatus()` — the control request that adds `error`, `scope` and `tools` — only when a server is newly not connected. Detail survives while a server's status is unchanged and is dropped on a change, since an error for a state the server has left is misleading. An unknown status string is treated as `pending` rather than thrown on.

**Nothing is drawn while every server is connected.** That is the common case and should cost no pixels; a failure gets a red pill, `needs-auth`/`pending` an amber one, and clicking opens the full list with the error text. `openroom-voice` not being connected is reported as "Voice tool unavailable" whatever its status says, because `speak` is broken if it is not up. `disabled` servers count as fine.

**Deliberately not here:** a notification or HUD pip (a broken server is a configuration problem, not something that blocks a turn), and reconnect/toggle from the UI — `mcp_reconnect` and `mcp_toggle` exist, but the fix is nearly always the config, and the editor is one click away.

### Slash commands are a filtered pass-through

The CLI executes any `/name` that arrives on the streaming input generator — locally, with no model turn — so Open Room never interprets commands itself. What it owns is in `src/shared/slash-commands.ts`, pure and tested: which commands are offered, how a draft is read, and how command output is told apart from the model's.

**Which commands appear is a decision, not a reflection of the list.** `supportedCommands()` reports 47 with `settingSources: []`, and perhaps six matter in a day. `visibleCommands` keeps a short allow-list of session commands (`clear`, `compact`, `context`, `usage`, `rename`, `autocompact`) and every skill it has never heard of, and drops a deny-list of CLI configuration commands (`init`, `config`, `mcp`, `heapdump`…), anything the init message lists under `terminal_slash_commands`, and `model`/`effort` — `SessionControls` is the honest UI for those, and their echoes already have to be filtered out of the transcript. A user's own skills therefore appear without this file learning their names.

**Only a slash in the first column is a command.** `parseCommand` treats a leading space, `//` and `/usr/bin/env` as prose. An unrecognised command is refused inline by `submitAction` rather than sent — the CLI would answer "Unknown command" harmlessly, but a typo that produces a reply looks like it did something. Before the list has loaded there is nothing to judge against, so everything is sent.

**Command output is stamped, not inferred.** The CLI marks it `model: "<synthetic>"` on the assistant message; `isSyntheticAssistant` renders it as "Command output" rather than as the agent speaking. The result that closes a command has `num_turns: 0` and all-zero usage — `isCommandResult` keeps it out of the running totals, out of the silence fallback (nobody wants the `/context` table read aloud), and out of the transcript, where "Turn complete · 0 turns" said nothing the output had not.

**The list is fetched once per session.** The init message is re-sent every turn; `supportedCommands()` is a control round trip, so it runs on the first init only and the list is replaced on `commands_changed`. That sequencing is `commandListUpdate`, a reducer the supervisor merely executes — the same shape as `overrideControlCalls`, and for the same reason: fetching on every turn or never replacing the list are both silent. Likewise `pickAction` decides whether choosing a command fills the draft or runs it, so the keyboard handler in `agent-chat.tsx` holds no decisions of its own. The list stays on the runtime after the session ends, since it is a property of the CLI rather than of a conversation.

### Model, effort and permission mode change from inside the conversation

`AgentConfig` fixes all three, so answering "just plan this one out first" used to mean opening the editor and restarting the session — losing the conversation's context in order to change how it was going to be continued. `SessionControls` in the pane header changes them for the running session, and `src/shared/session-overrides.ts` holds every decision about what that means.

**They are sticky, not per-turn, because that is what the SDK does.** `setModel` changes the model "for subsequent responses" and stays until something changes it back; the same is true of `setPermissionMode` and `applyFlagSettings`. Simulating a one-turn override on top would mean reverting behind the user's back, and an interrupt or a crash mid-turn leaves that revert ambiguous. Ending the session drops them and the config takes over again — kept in `stop()`, so an agent never quietly starts its next conversation in plan mode because of something set days ago.

**Overrides apply at session start as well as through the control methods.** The control requests only exist once a session is live, so an override set before the first prompt would otherwise be ignored for exactly the turn it was set for. `agentQueryOptions` takes them as a fifth argument for this.

**Effort goes through `applyFlagSettings({ effortLevel })`, not a setter of its own.** There is no `setEffort`. The flag settings layer sits above user/project/local settings and is unaffected by `settingSources: []`. Clearing must pass `null` rather than `undefined` — `undefined` is dropped in serialization and would silently leave the previous value in place.

**Only what changed is sent.** Each control request is a round trip to the CLI. `overrideControlCalls` returns the calls as data and the supervisor executes them, so the decision is testable while the executor stays four lines with an SDK in front of it — the same reason `agentQueryOptions` was extracted.

**`acceptEdits` is offered here but deliberately absent from `AgentConfig`.** It is useful for a refactor where approving every write is the friction, and much less so as a standing default that outlives the session it was turned on for. `bypassPermissions` and `dontAsk` are never offered, and `sanitizeOverrides` rejects them in **main** rather than trusting the renderer only ever to send safe values.

**`auto` is offered, in both the config and the session controls, and it is bounded.** It hands routine approvals to the SDK's classifier — the same mechanism as Claude Code's own auto mode — and escalates the rest through the ordinary prompt; nothing in the app can turn that escalation off, which is what separates it from `bypassPermissions`. Measured on `claude-sonnet-5`: two Bash calls, one a file deletion, ran with `canUseTool` never firing, so it is a real transfer of trust and stays a choice rather than the default. **Not every model supports it, and the SDK does not say so.** Measured on `claude-haiku-4-5` (`supportsAutoMode: null`): the query started and the init message reported `permissionMode: "default"` — a silent downgrade. The supervisor records the init's mode on `AgentRuntime.permissionMode`, and `permissionModeNotice` turns a mismatch into a line under the session controls; without it, auto on Haiku would look selected and change nothing.

**Every group leads with "Agent default", which clears the override rather than writing the config's current value into it.** An agent edited later should follow its new config, not a copy of the old one taken when someone happened to open the menu. Relatedly, `overriddenFields` ignores an override equal to the config's own value, so re-picking what the agent already had does not light the "changed" badge.

**Changing the model makes the CLI echo it back as user content, twice, by different routes.** Live, `setModel` emits `<local-command-stdout>Set model to claude-sonnet-5</local-command-stdout>` as a `user` message. The persisted session *also* stores the invocation as a `<command-name>/model</command-name>` block, which comes back on the next launch. `isCommandEcho` filters both. This is the `rate_limit_event` failure mode again — nothing errors, the transcript just fills with XML nobody typed — and the second form survived the first fix precisely because it only appears after a restart.

**`condenseForSpeech` sets it too, for isolation only.** Measured either way it makes no difference to that call's latency, which is dominated by the round trip — so do not remove it expecting to reclaim time, and do not add it elsewhere expecting to save any.

### Pointing and receiving: images, `@file`, files changed, queued prompts

Open Room is a delegation surface beside the user's editor, not an editor. Phase 5d added the things that make pointing an agent at something and seeing what it did cheap, and stopped short of anything an editor already owns.

**Images travel as content blocks, never as files.** A pasted screenshot has no path; `readImage` turns the `File` into base64 and `userContent` builds the SDK's `image` block. Text-only prompts stay a plain string so `isCommandEcho`, `parseCommand` and the bubble keep reading what they always did. Limits (`MAX_IMAGES`, `MAX_IMAGE_BYTES`) are applied in the renderer for the message and again in main, because a renderer is not a trust boundary. A 1×1 test pixel makes the model say it sees nothing — verify image delivery with a real image. The same trust rule covers the text: `acceptPrompt` refuses a blank or whitespace-only prompt with no images in main, because measured over IPC an empty string spawned a whole CLI session to say nothing and a whitespace prompt sat in the queue as a turn. The composer's disabled send button only ever guarded the UI route.

**`@file` is sent as typed.** The agent has `Read`; expanding the file into the prompt would duplicate it into the context window and alter what the user said. `mentionAt` only opens the picker for an `@` at the start or after whitespace, and closes it once the user types a space. That rule cannot tell a scoped package name from a file reference: `me@example.com` never opens the picker, since the `@` is mid-word, but `@radix-ui/react` typed after a space does — guessing which slash-delimited string the user meant would be worse than opening the picker every time. Escape closes the picker without touching the draft (`dismissedMention`). Dropped paths are relative when inside the workspace (`mentionFor` checks on a separator, so `app2` is not inside `app`).

**Attached files are chips in the composer, mentions on the wire.** A non-image file — dropped, or picked through the paperclip's hidden `<input type=file>` — becomes a chip beside the image thumbnails: a type icon (lucide, keyed by `fileIconKind`), the basename, and the full path on the `title` tooltip. The chip is display only: `appendMentions` (`src/shared/file-attachments.ts`, tested) serializes the chips back into exactly the `@path` mention a drop used to type into the draft — relative inside the workspace, quoted on a space — appended to the outgoing text, so the agent and the transcript bubble both see the same honest `@` reference and nothing about "sent as typed" changes. Verified end to end: two dropped files rendered chips and a send produced `ignore these files, just reply ok @drop-me.ts @"read me.md"` in the bubble. Chips are deduped case- and separator-insensitively (Windows paths arrive spelled both ways), a send failure restores them along with the draft (measured, via a workspace-missing rejection), and a draft that parses as a slash command sends *without* them — the mention would become the command's arguments — leaving the chips pending for the next real prompt. A `File` with no real path (`pathForFile` returns `''`) is refused with an inline message rather than attaching a chip that references nothing. The typed `@` picker is untouched: text the user writes stays text.

**Files changed is read off the transcript, not a watcher.** `filesChangedIn` collects `Edit`/`Write`/`MultiEdit`/`NotebookEdit` targets between one prompt and the next result; a watcher would also see the user's own editor saving. Persisted transcripts from `getSessionMessages` carry no `result` messages at all — only `user`/`assistant` — so the history list cannot end a turn at a result the way the live one does; both lists instead end a turn at the next `isPrompt` boundary, exported from `files-changed.ts` for this. A compaction summary is a `user` message too but is not a boundary: `isPrompt` excludes anything flagged `isSynthetic`.

**Open in editor never spawns a shell.** The target path comes from the agent's own Edit/Write tool inputs, not from the user, so `openInEditor` resolves the executable itself rather than trusting a shell to find it: `resolveExecutable` walks PATH, trying PATHEXT suffixes before a bare name because a real PATH held both an extensionless `code` shebang and a working `code.cmd` side by side, and the bare lookup would resolve to the one `spawn` can't execute. A resolved `.cmd`/`.bat` target runs through `cmd.exe /d /s /c` with the whole argv quoted inside one pair of double quotes (`spawnPlan`), and every argument is refused if it contains `" % !` or a line break, since `%` and `!` expand under cmd's own parsing before quoting has any effect. The empty-command default (`shell.openPath`) refuses an executable target (`isExecutableTarget`) because `ShellExecute`'s open verb *runs* `.bat`/`.exe`/`.lnk`/etc. rather than displaying them, and normalises the basename the way Win32 does — trailing dots and spaces stripped, since `notes.bat.` resolves to the real `notes.bat`, and a `:` treated as an alternate data stream — since a raw extension check would miss both. A spawned command that exits non-zero within 1500 ms is reported as broken; with `shell: true` the spawn event was only ever cmd.exe starting, which is why that check exists at all.

**Queued prompts are held in main.** `query.interrupt()` takes no arguments and cannot cancel a message the CLI already holds, so pushing early would make Stop a lie. `shouldQueue` decides whether a submission waits; `queueActionForResult` decides what happens when a turn ends — a command result and a successful turn both dispatch the next queued prompt, an error or an interrupt clears the queue — and one `settleQueue` executes it. `stop()`'s final patch and `dropQueued` both clear the queued row even when the session is already gone, so the pane never shows a prompt that will never be sent. The CLI's own permission engine auto-approves read-only commands such as `git status` before `canUseTool` is even consulted, so those never raise a prompt in Open Room.

**A changed file's row shows a read-only diff, and it is a diff of the file now, not of the turn.** A `Diff` toggle on each row fetches `fileDiff(agentId, path)` lazily — a turn can touch dozens of files and most rows are never opened. Main runs `git diff <base> -- <path>` in the conversation's checkout via `src/main/git.ts` (an argv array to `spawn`, never a shell; every path after `--`; `git` found with the same `resolveExecutable` the editor command uses), where `base` is `HEAD` in the workspace and the recorded base commit for a worktree conversation, so committed work shows there too. An untracked file goes through `git diff --no-index -- /dev/null <path>` so a freshly written file renders as all additions — measured working on Windows, where Git for Windows maps `/dev/null`. `src/shared/unified-diff.ts` parses hunks into old/new line numbers and `DiffView` draws them; no diff library. The label says which base ("vs HEAD" / "vs the branch base") because the result includes later turns and the user's own edits — a snapshot per turn would need the transcript to carry file contents it does not have. Over 200 KB, binary, and "nothing differs" are each said in words rather than rendered. Rows are labelled relative to the conversation's checkout (`displayPath`), since a worktree path is long and identical for every file; the full path stays on the tooltip and in the actions.

**Permission detail: the `edit` kind carries `edits: { before, after }[]`**, one entry per `MultiEdit` edit, rendered as before/after pairs; a plain `Edit` is the same shape with one entry. Every detail block is bounded (`max-h-64`) rather than letting a large diff or command take over the prompt.

## Packaging

`electron-builder.yml` produces an NSIS installer on Windows and a DMG on macOS; Linux is not a target. Nothing is bundled beyond the app and its dependencies — no voices, no speech models — and there is no auto-update (the scaffold's `publish` block pointed at a placeholder URL and was removed). Unsigned and unnotarized per the Phase 0 decision. The Windows installer is about 280 MB, almost all of it the SDK's `claude.exe` and `onnxruntime`.

**Removing the `publish` block does not stop electron-builder publishing.** On a tag build it reads `GITHUB_REF_TYPE`/`GITHUB_REF_NAME` (set by GitHub Actions on every tag run), switches its publish policy on, infers a GitHub target from the git *remote* with no config at all, and exits wanting `GH_TOKEN` — which is how the first `v0.1.0` run failed on both platforms after every check passed. The release workflow's Package step passes `--publish never` for this; uploading is the release job's business. Reproducible locally by setting those env vars before `electron-builder`, which is also how the fix was proved.

**The SDK's bundled `claude` must be spawned from outside the asar, and the SDK does not know that.** `@anthropic-ai/claude-agent-sdk-<platform>-<arch>` is an optional dependency carrying the CLI binary, and the SDK spawns it by default, resolving it relative to its own module. In a packaged app that module is inside `app.asar`, so the resolved path is too, and nothing can execute from within an archive. Measured on the first packaged build: the login check reported signed-in (it already rewrote the path) while every agent failed with "exists but failed to launch". `bundledClaudePath()` in `src/main/claude-binary.ts` resolves the package and rewrites `app.asar` → `app.asar.unpacked`; every `query()` — agents and `condenseForSpeech` — passes it as `pathToClaudeCodeExecutable`. `agent-options.test.ts` pins it. The package is listed in `asarUnpack` explicitly along with `onnxruntime-node` and `@img/*` rather than relying on electron-builder's `.node` heuristic, which would miss a plain executable.

**The sidecar itself runs fine from inside the asar.** `voice.js` is spawned with `process.execPath` and `ELECTRON_RUN_AS_NODE=1`, and Electron's Node reads asar members; the native `.node` files it requires are redirected to the unpacked copies. Verified by sending `ping` to the packaged sidecar and getting `pong`.

**Login is detected, not driven.** `src/main/login-check.ts` runs the bundled binary's `auth status --json` at launch, on request, and whenever an agent fails `not-authenticated`, and holds the result as account state beside quota. `parseAuthStatus` reports anything unreadable as `unknown`, never `signed-out` — a false signed-out would lock a working install behind the first-run screen, while unknown lets agents try and report for themselves. `FirstRun` replaces the whole window while no usable login exists: install Claude Code, run `claude` and sign in, check again. The login is a browser-plus-terminal flow the CLI owns and cannot be run from inside the app. `ANTHROPIC_API_KEY` is stripped from the check's environment for the same reason it is stripped from agents.

**A login belongs to an environment, not to the machine, and the gate is per environment.** The host's `~/.claude` and each WSL distro's are separate, so a token can expire on Windows while the distro stays signed in. The first version held one host status and locked the whole window behind `FirstRun` on it; the field report was an install whose agents all ran in WSL, signed in there, shut out because the Windows terminal's OAuth had expired. `LoginSnapshot` (`src/shared/login.ts`) holds `host` plus one status per distro some agent uses; `recheckLogin` probes them in parallel (`WslRuntime.checkLogin`, one `wsl.exe` spawn each), and a new agent saved into an unprobed distro triggers one more. `loginGate` shows `FirstRun` only when every environment the agents use is known signed out, with the host as the environment when there are no agents yet; `unknown` never locks out. Otherwise each affected agent carries `loginNotice` as an amber line under its pane header, the same slot as the plan-lacks-Fable line, with the host or distro sign-in command. `FirstRun` lists one step per signed-out environment. The model-access probe still hangs off the host login, since it reads the host binary's picker; a distro-only login leaves it `unknown`, which allows everything. This is the same shape T3 Code arrived at: one backend per environment, each reporting its own provider auth, sign-in a skippable onboarding step and an in-chat banner afterwards, never a wall. Tested against stubbed snapshots; the host-out-distro-in case has not been run live on this machine, which has no distro with Claude Code installed.

**Verifying the packaged build is scripted, not clicked.** `dist/win-unpacked/open-room.exe` is what the installer lays down, so it is launched directly with an isolated `OPEN_ROOM_HOME`, `--user-data-dir` and `--remote-debugging-port`, and driven over CDP through `window.openRoom`. The PATH is reduced to `System32`, `Windows` and `System32\WindowsPowerShell\v1.0` so no dev toolchain is reachable — the last entry is on every real install and the system TTS path needs it. **Launch it from PowerShell, not Git Bash**: `env -i PATH=...` in Git Bash mangles a Windows-style PATH on the way into the child, and the symptom was `spawn powershell.exe ENOENT` with the directory plainly listed — an hour of chasing a bug the app did not have. An empty `USERPROFILE` makes the bundled CLI report signed-out, which is how the first-run screen is exercised.

**The dev app is driven the same way: `npx electron-vite dev --remoteDebuggingPort 9433`.** That flag is electron-vite's own; `ELECTRON_EXTRA_LAUNCH_ARGS` and `npm run dev -- --remote-debugging-port` both start the app with no debug port and no error. `http://127.0.0.1:<port>/json` then lists the main window at `http://localhost:5173/` and the overlay at `/overlay.html`; Node 22's global `WebSocket` reaches `webSocketDebuggerUrl` with no package. Two things bite: `Runtime.evaluate` calls share one global lexical scope, so a bare `const` in two snippets collides — wrap every snippet in an IIFE; and a hung `curl` against a dead port keeps it listening for a later run, so a port that is "in use" with no electron process is a stale client, not the app. Synthesized `DataTransfer` events exercise the paste and drop handlers, but `webUtils.getPathForFile` needs an OS-backed `File`, so a genuine Explorer drag cannot be reproduced over CDP. Kill `electron.exe` and the electron-vite node process afterwards.

**macOS is configured but unverified.** The DMG target, the microphone usage string and the entitlements are in place; nothing here has been built or run on a Mac.

### Updates are announced, not installed

`UpdateChecker` (`src/main/update-check.ts`) asks GitHub's releases API for the repository 15 s after launch and every six hours, compares against `app.getVersion()`, and the result lands in three places: `UpdateBanner` at app level (same shape as `QuotaBanner`: pulled on mount, pushed on change), an "Update to x.y.z…" item in the tray menu, and one native notification per version (`shouldNotifyUpdate`). Download opens the release page in the browser. The decisions are in `src/shared/updates.ts`, pure and tested; the checker's schedule is tested with fake timers.

**This is the one request the app makes to a server that is not Anthropic's.** It carries `User-Agent: open-room/<version>` (GitHub refuses requests with none) and nothing else. The README's "everything stays local" paragraph says so, and `checkForUpdates` in settings turns it off. Off means off: disabling it resets the status to `unchecked` so a banner from a check the user just switched off does not linger. `net.fetch` rather than Node's `fetch`, so the request follows the system proxy.

**Releases flagged prerelease count.** Every Open Room release so far carries the flag, and GitHub's `releases/latest` endpoint excludes them, so the check reads `/releases` and picks the highest version that is not a draft. If a real beta channel ever exists, `readRelease` in `updates.ts` is where that changes. The check also never offers a downgrade, since a development build usually sits ahead of the last tag.

**The Updates page offers the same action as the banner, through the same hook.** `useUpdate` (`hooks/use-update.ts`) holds the snapshot, the action from `updateAction`, the refusal from the last click, and `act`; the banner and the settings page both read it, so a found update reads the same in both places. On the page, once a version is known the filled primary button takes "Check now"'s place (Download, then "Downloading 42%", then "Restart to update"; "Open release page" where in-app install is unsupported or failed) and the version line stays under it. "Check now" has nothing left to find once an update is known.

**The banner's "Later" is per version and lives in the renderer's localStorage.** It is display state that nothing but the banner reads, and the tray item ignores it, so hiding the banner never hides the update. A downloaded installer outranks the dismissal: once the button reads "Restart to update" the banner stays until it is used.

### On Windows the update installs from inside the app

`UpdateInstaller` (`src/main/update-install.ts`) wraps electron-updater's `autoUpdater` behind a five-member `UpdaterLike` so its decisions are tested against a stub. Main hands in `autoUpdater` only on `win32` in a packaged build and null everywhere else; `UpdateInstall.kind: 'unsupported'` is what the banner reads to fall back to opening the release page. electron-updater's docs are blunt that macOS auto-update needs a signed app, and this one is unsigned, so the Mac path stays banner-and-browser until signing exists.

**Discovery and install are two different feeds, on purpose.** `UpdateChecker` reads the releases API, which works for every release ever tagged. electron-updater reads a `latest.yml` attached to the release, which exists only from the first release built with the `publish` block in `electron-builder.yml`, so the checker can find a version whose feed does not exist. Download therefore runs electron-updater's own check at click time, and "no update available" from it is reported as `failed` with "No installer is published for this release yet", which the banner turns into an "Open release page" button with that line under it. A dead button was the alternative.

**The `publish` block is the feed address, not a publish instruction.** It makes electron-builder write `resources/app-update.yml` into the app and `dist/latest.yml` beside the installer; the workflow still passes `--publish never` and uploads `latest.yml` and the `.blockmap` itself (see the artifact list in `release.yml`). Forgetting either file makes every Download fall back to the page. `allowPrerelease` is set on `autoUpdater` for the same reason the checker counts prereleases: every release so far carries the flag, and electron-updater's GitHub provider would otherwise consult `releases/latest` and find nothing. No `publisherName` is embedded, since the build is unsigned, so `NsisUpdater.verifySignature` returns null and the download is not signature-checked. That is the same trust as downloading from the release page by hand; a signed build would change it.

**Restart is refused while any agent is `working` or `starting`.** Each is a CLI subprocess mid-turn, and the user should decide whether to stop it. The refusal names the count and lands under the banner. When it goes ahead, `prepareQuit` sets `quitting` (the window otherwise refuses to close, see "There is no `window-all-closed` handler") and awaits `supervisor.stopAll()` *before* `quitAndInstall`, so the installer never finds `claude.exe` children still running. `autoInstallOnAppQuit` is left at its default, so an installer downloaded and not yet used runs silently the next time the app quits by any route.

**Measured on a packaged NSIS build with the version lowered to 0.1.0:** the banner offered 0.1.1 with `install.kind: 'idle'`, Download ran electron-updater's check against the real v0.1.1 release, which has no feed, and the phase went to `failed`; the button became "Open release page" with the reason under it. The first attempt rendered electron-updater's whole `HttpError`, response headers and stack trace included, under the button; `failureLine` keeps the first line and maps "Cannot find latest.yml" to "No installer is published for this release yet". **Not measured:** a download that succeeds and the restart itself. That needs a tagged release carrying `latest.yml` to update *from*, which none has yet; the first release after this lands is where it gets exercised.

**`electron-builder --dir` writes no `app-update.yml`.** Only a real target build (`--win nsis`) does, so `npm run build:unpack` produces an app whose Download fails with `ENOENT ... app-update.yml` and falls back to the page. Verify anything about the in-app updater against `npm run package` output, not the unpacked folder. Also: launching `dist/win-unpacked/open-room.exe` while electron-builder is still writing that folder makes the build fail with `EPERM: operation not permitted, unlink ... d3dcompiler_47.dll`, and the app that launched is last time's, which is how a stale preload was probed for ten minutes here.

## Quota and concurrency

N concurrent agents on one subscription is the app's premise and its most likely real-world failure. Rate-limit and overload responses are routine here, not exceptional.

- Surface `usage` and cost from `SDKResultMessage` per agent and per session. These are **cumulative across turns** in streaming-input sessions — each result carries the running total, so read the latest rather than summing.
**Context pressure comes from the ordinary result message, not from `/context`.** `AgentRuntime.contextUsage` is derived in the supervisor by `contextUsageFrom`, and the pane renders it with `ContextMeter`. Three things there are measured rather than assumed, and each of them is a silent wrong answer if got backwards:

- **`usage` is per-request; `modelUsage` is cumulative.** Observed in a single result: 37,475 cached tokens on `usage` against 74,901 on `modelUsage`. Using the cumulative one grows without bound and reads as a window filling twice as fast as it is.
- **Cache reads dominate a warm conversation.** `input_tokens` alone was 10 for a 37,628-token prompt, so occupancy must be `input + cache_read + cache_creation`. Counting only `input_tokens` reports an empty window for a nearly full one.
- **`modelUsage` can hold several models** — subagent and internal calls land there too — so the agent's own model is preferred and the *largest* window is the fallback, never whichever key enumerates first.

Verified across three turns of one conversation: 37,755 → 37,888 → 38,005 against a fixed 200,000.

**The rich breakdown is a control request, not a slash command.** `query.getContextUsage()` returns the per-category rows, MCP tool token costs, memory files, skills, and a `messageBreakdown`, plus `isAutoCompactEnabled` and `autoCompactThreshold`. An earlier note here said this was "attached only to a `/context` result" and therefore gated on slash command support — that was read off the `context_usage` field on the assistant message and was wrong: the same data is reachable directly, and nothing about the detailed card depends on the command surface.

**The meter's bands anchor to `autoCompactThreshold`, and the value is absolute tokens.** Measured on a real session: 167000 against a 200000 window, not a fraction — a wrong unit here misplaces every band silently. The supervisor reads it via `getContextUsage()` once per session on the first init (the init is re-sent every turn; the control request is a round trip, same shape as the command-list fetch) onto `AgentRuntime.autoCompact`, kept when the session ends since it is CLI configuration. `contextSeverity` then hangs the bands off the compact point: red within 5 points of it, amber within 15 (`compactAnchor` in `context-usage.ts`); auto-compact disabled anchors to 1.0 because the cliff is then the window itself, and nothing reported yet keeps the legacy 70/90%. `/autocompact` changing the threshold mid-session is deliberately not tracked — the next session reads it fresh. The rest of the `getContextUsage()` payload (categories, message breakdown) is still unread; the detailed context card remains unbuilt.

**Compaction is triggered by sending `/compact` through the streaming generator.** There is no `compact()` on `Query` and no compaction control request, but none is needed: the CLI executes slash commands that arrive as user messages. An earlier note here said the opposite, on the strength of `/context` apparently returning "What would you like me to do with that path?" — re-measured on 0.3.233 in a real session, `/usage`, `/compact` and `/context` all ran locally, so treat that note as refuted rather than as version drift to watch for. See "Slash commands are a filtered pass-through" above.

**Compaction does two things to the stream that misrender if taken literally.** Measured on a manual `/compact` (48,086 → 876 tokens): the summary arrives as a *user* message flagged `isSynthetic: true`, and the messages preserved across the boundary are re-emitted under their original uuids, timestamped before the boundary. `src/shared/compaction.ts` names both — `isInjectedSummary` renders the summary as a collapsed "Context summary" block rather than a bubble the user apparently typed, and `replayKey` lets the supervisor drop a conversation message whose uuid it has already appended. The `<local-command-stdout>Compacted </local-command-stdout>` echo that follows is caught by `isCommandEcho` already.

`compact_boundary` renders as a divider in the transcript carrying the trigger and the before/after token counts. It is a `system` message, so `isRenderable` grew a `VISIBLE_SYSTEM_SUBTYPES` allow-list rather than dropping the blanket filter — a new status subtype must not start rendering as a JSON dump just because it appeared.

- **The SDK emits `rate_limit_event` with structured subscription quota.** Measured payload, captured from a real turn:

  ```json
  {"status":"allowed","resetsAt":1787243400,"rateLimitType":"five_hour",
   "overageStatus":"rejected","overageDisabledReason":"org_level_disabled_until","isUsingOverage":false}
  ```

  This is the honest answer to "why did my agent stall", and it only exists for subscription users, which is every Open Room user by design. It is surfaced on `AgentRuntime.rateLimit` and rendered as a banner, not left buried in the transcript.

  An earlier note here listed `utilization` as part of the payload. It was not present in what the SDK actually sent, so treat `RateLimitStatus.utilization` as optional-and-usually-absent rather than as a number to render — nothing reads it today. `overageStatus` and `overageDisabledReason` are real and are *not* read yet; they matter because `overageStatus: "rejected"` means hitting the window blocks rather than rolling onto overage, which changes what a "limit reached" banner should say.

- **Quota is account state, not agent state.** Every agent draws on the same Claude Code login, so a limit is a property of the account that merely happens to be *reported* on one agent's turn. It was rendered as a banner inside `AgentChat`, which meant it appeared only on whichever agent's turn carried the event: an idle agent showed a clean pane while being equally blocked. It is now held once in main as `accountQuota`, broadcast on `quota:changed`, and rendered by `QuotaBanner` at app level. The renderer pulls with `getQuota()` on mount as well as subscribing, because a window opened after the last event would otherwise show nothing until the next turn ran.

- **A quota stall needs an out-of-window channel.** This app expects the main window to be hidden while agents work — that is what the HUD and notifications are for — so a condition visible only in a chat pane is one nobody finds. Quota now sets a `paused` pip (distinct from `needs-attention`, whose roster label is literally "needs permission" and would be a lie here) and fires one native notification via `shouldNotifyQuota`, which returns true only on a step up in severity. The event arrives about once per turn, so notifying on anything else would be relentless.

- **The `paused` pip keeps breathing, slower and dimmer.** Same colour, since colour means *which agent*. Not still: the reduced-motion block already records why — "a still dot cannot be told from a stale one".

- **Failures classify from the structured event, not the error text.** `classifyFailure` checks `runtime.rateLimit?.status === 'rejected'` before falling back to matching "rate limit" or "429" in prose, and carries `resetsAt` through as `retryAt`. The string match only worked when the message happened to say so, and never knew when a retry was worth attempting.

- **Say only what the payload says.** `overageBlocked` is positive knowledge only: an absent `overageStatus` means the event did not say, so the copy stays at "limit reached" rather than claiming agents are paused. A first version treated unknown as unavailable and its own test caught it.

- **It fires roughly once per turn, whatever the state.** Almost always `status: "allowed"` — it is a heartbeat, not an alarm. `describeRateLimit` returns `null` for `allowed`, so the banner correctly stays hidden; but the message still reaches the transcript, because `AgentSupervisor.handleMessage` appends *every* SDK message before dispatching on type. It therefore has to be excluded in `isRenderable` as well, or it hits the debug fallthrough in `TranscriptMessage` and renders as a JSON dump in every chat. That is a silent failure mode: nothing errors, the chat just fills with noise. `SILENT_TYPES` is the single list to add to, and `transcript.test.ts` guards it.
- **A reached limit clears itself when its window resets, and can be collapsed but not made to vanish.** The `allowed` event that used to clear the banner arrives once per turn, so a limit hit at midnight stayed on screen until someone ran an agent after the reset. `msUntilReset` (`quota.ts`) reads the payload's own `resetsAt`; main sets one timer per report and clears `accountQuota` when it fires, unless a newer report has replaced it, and the next turn confirms either way. The banner's X is a dismissal keyed by `quotaKey` (window, severity, reset time), so the heartbeat repeating the same limit does not bring it back and a changed one does. A reached limit collapses to `QuotaPill` in the title bar's trailing slot, clickable to restore, because agents are paused and that has to stay visible somewhere; a warning dismisses outright. Dismissal is renderer state and dies with the window on purpose.

- Rate-limit, overload, and usage-cap conditions are **first-class agent states**, visually distinct from "crashed" — one is wait-and-retry, the other needs intervention.
- Cap max concurrent running agents (user-configurable) and tear down idle sessions. Each agent is a full `claude` CLI subprocess; five idle agents is multiple GB.

## TTS voices and models

**Nothing is bundled; the OS voices are the floor.** Everything else downloads on demand.

Providers, in order of default preference:

- **System voices** — macOS `AVSpeechSynthesizer` via `say`, Windows SAPI5. Always present, instant, offline, no download, and useful for distinguishing many agents at zero cost. Platform-specific, so a config naming a macOS voice means nothing on Windows — which is what the empty-id default below is for.
- **Kokoro** — opt-in per agent, downloading 163 MB of weights on first use. Identical on every platform, Apache-2.0 throughout.

**Synthesis always writes a WAV; playback is a separate short-lived process.** Stopping is then just killing that process, which is what makes preemption and barge-in possible at all. A fire-and-forget "speak this string" API cannot be interrupted mid-sentence, so this shape is load-bearing rather than incidental — and both backends share it.

**The sidecar is spawned with `process.execPath` and `ELECTRON_RUN_AS_NODE=1`**, so it runs on Electron's own Node and users need no separate runtime. It is built as a second rollup input of the `main` bundle, landing at `out/main/voice.js`.

**PowerShell is invoked with `-EncodedCommand`.** Speech text is arbitrary model output; quoting it onto a command line loses to apostrophes, quotes and newlines. Base64 sidesteps escaping entirely.

**Every PowerShell script text must be a constant, and this is worth more than it sounds.** Windows hands each script buffer to AMSI before the first statement runs, and Defender's verdict is cached against the *content*. A script that never varies is scanned once for the life of the machine; a script carrying an interpolated path is scanned every single time. Measured over five spawns of the same command: unchanging cost 688 ms once and then 131/147/137/138 ms, while a script differing only in one embedded path cost 708/705/688/677/674 ms and never improved. PowerShell's own report of the time elapsed before our first statement tracks it exactly — 663 ms against 108 ms — so it is the scan, not the work.

Both `SAPI_SCRIPT` in `synth.ts` and `PLAY_SCRIPT` in `player.ts` therefore read every per-utterance value from the environment, where AMSI does not look. Interpolating the temp path used to make both unique per utterance, which put roughly 550 ms in front of *each* of them — about 1.2 s before an agent made any sound, on every line it spoke, for system voices. Kokoro pays it once rather than twice, since it synthesises in-process and only playback shells out. `src/voice/synth.test.ts` and `player.test.ts` guard it by asserting the encoded command is byte-identical across two different utterances; anything that appends a value to those strings reintroduces the delay silently, because the audio is unchanged.

**The sidecar is primed at start, and it needs both scripts.** There are two one-time costs and neither is synthesis. Measured on a fresh sidecar against its own steady state: synthesis 1384 ms against 290 ms, playback 811 ms against 261 ms of overhead around the clip. Priming with an unrelated PowerShell call (`listVoices`) absorbed only half the first — 1384 ms fell to 830 ms — so one cost belongs to the process's first spawn and the other belongs to each distinct script text. `warmSpeech` therefore runs the real `SAPI_SCRIPT` and the real `PLAY_SCRIPT`: anything cheaper warms the spawn and leaves both scans for the user's first sentence. With it, the first utterance measured 3211 ms against a 3216 ms steady state — the penalty is gone rather than reduced.

The synthesised clip is discarded rather than played; playback is warmed with a WAV of silence this app generates itself, because a launch must never make a noise and that is only guaranteed by owning the samples. `warm.test.ts` asserts every sample is zero and that the header's declared lengths match the bytes present — a player trusting a wrong length can emit whatever follows in memory.

**Priming hangs off the sidecar starting, not off `whenReady`.** The cost follows the process, and the sidecar restarts itself after a crash, so warming once per app launch would leave the first utterance after any crash slow again — silently, and only in the field. `VoiceSidecar` takes an `onStart` callback invoked after every successful spawn; `voice-sidecar.test.ts` covers the restart case and the deliberate-stop case. It is gated on some agent having TTS enabled, and Kokoro's weights are loaded only when an agent actually selects that engine — a warm-up is no place to start a 163 MB download.

**`speak` resolves when playback finishes, not when it starts.** Timing it end to end measures the clip, so a 2.7 s utterance reports ~3.3 s no matter how fast synthesis is. Any latency claim has to subtract the clip or instrument PowerShell from inside — most of the confusion in this area came from not doing that.

**`rate` means 1 is natural and higher is slower** — inherited from Piper's `length_scale` and kept after Piper was dropped, because agent configs already used it. Every backend's own scale is mapped onto it, so a config means the same thing everywhere: SAPI's −10..10 is inverted, macOS `say` takes words per minute, and Kokoro's `speed` is its reciprocal.

**An empty system voice id means the platform default.** A config naming a specific voice travels badly between machines; empty always resolves to something.

**System TTS on Windows must synthesize to WAV and play through a player we own.** Spawning PowerShell with `System.Speech.Synthesis` carries ~200–400 ms startup per utterance and cannot be cleanly interrupted mid-sentence, which the bus's preemption and barge-in requirements both need. Killing the child stops audio, but owning the player is what gives clean interrupt and a seek position. This is why system voices are a variety option and not the baseline.

**Installed is not loaded, for Kokoro too.** `kokoroStatus` reports both, and only `installed` — a disk check for the files transformers.js caches — may decide whether to offer a 163 MB download. Reporting `loaded` alone meant the sidecar's empty memory at launch read as "not downloaded", so the editor demanded the download again after every restart, for every agent, with the weights already on disk. `sttStatus` and `vadStatus` always drew this distinction; Kokoro was the odd one out because `ModelManager` does not own its download and there is no catalogue entry to ask. An installed-but-cold model is warmed by the editor rather than prompted for — it takes about a second, needs no network, and there is nothing for the user to decide.

**Voice resolution must degrade, never fail.** Configs routinely reference voices that were deleted, never downloaded, or belong to the other OS. Chain: configured voice → the platform default (an empty system id always resolves to something) → a notification. A missing model must never crash the sidecar or produce silent failure.

**Two backends exist: system voices and Kokoro.** System voices are the default — instant, offline, no download. Kokoro is opt-in per agent and downloads 163 MB of weights on first use. The sink falls back to notifications whenever TTS is off, the sidecar is down, or synthesis throws.

**Piper was evaluated and rejected.** Its maintained build is GPL-3.0 and ships only as Python wheels; the permissive build was archived in 2023; and its voices carry a patchwork of dataset licences including non-commercial ones (`ryan`, `hfc_female`, `hfc_male` are CC BY-NC-SA). Kokoro is Apache-2.0 across engine, weights and all 28 voices, with no external binary. Do not reintroduce Piper without revisiting all four points.

**Kokoro uses `fp16`, and the choice is counter-intuitive.** Measured for a 2.4 s utterance: q8 1883 ms, fp16 624 ms, fp32 586 ms. int8 has no fast path here, so the *smallest* quantisation is by far the *slowest*. Benchmarking q8 alone nearly caused the engine to be rejected.

**fp16 renders some lines as all NaN, and the same line every time.** Measured: 8 of 48 ordinary agent lines across six voices ("Should I commit these changes?" in `am_michael`), and 5 of 18 short phrases in `am_fenrir`. Saved as a WAV that plays as silence, with no error anywhere, so an agent simply said nothing. `renderAttempts` in `kokoro.ts` retries at 3% slower, 3% faster, then without the final punctuation; every one of 72 lines rendered after that. If all fail, `synthesize` falls back to the platform's default system voice, which is also where any other Kokoro failure now lands. fp32 was not measured for NaN: only the fp16 weights are downloaded.

**Windows SAPI synthesis is fast — about 265 ms (RTF 0.10).** An earlier note claimed ~2 s of PowerShell startup per utterance; that was a mis-measurement of speak-to-*completion*, which includes playback. There is no synthesis latency problem to solve on Windows.

**The neural stack must stay lazily imported.** `import('./kokoro')` happens on first use, not at module load: transformers.js pulls a large wasm phonemizer, and importing it eagerly wedges sidecar startup so even `ping` never answers.

**`@huggingface/transformers` is an explicit dependency on purpose.** As a transitive dep, electron-vite bundles it into the sidecar — 1.8 MB versus 7.8 KB externalised — and its inlined wasm floods stderr. It is also pinned to `^3.5.1`: installing it unpinned resolves to a `4.0.0-next` prerelease whose `onnxruntime-node` carries an advisory.

**`onnxruntime-node` is an explicit dependency, pinned to exactly `1.21.0`.** Explicit because electron-vite only externalises declared dependencies — bundled, its dynamic require of `onnxruntime_binding.node` fails at runtime, and only in the packaged build, since the dev path resolves differently. Pinned because `npm install onnxruntime-node` resolves to 1.27.0, which installs a *second* copy of a native runtime beside the 1.21.0 that `@huggingface/transformers` uses, and which carries a high-severity `adm-zip` advisory that 1.21.0 does not.

**`sharp` is pinned via an npm `override`.** `@huggingface/transformers` depends on it for image models Open Room never touches, and every version below 0.35.0 carries unfixable libvips CVEs. Removing the override reintroduces them.

**One `ModelManager` in the voice sidecar serves every downloadable model.** Shipped JSON catalog manifest (name, size, URL, sha256, license, attribution), resumable download with progress, checksum verification, partial-file cleanup.

**The Whisper models are ONNX and much larger than the GGML figures suggest** — `tiny.en` is 154 MB across seven files and `base.en` is 294 MB, not the 75/142 MB of the whisper.cpp builds. `scripts/verify-catalog.ts` fetches each file and regenerates `src/shared/model-hashes.ts`; the sizes and digests there are measured, never guessed. Keys are `<entry id>/<file name>` so a changed URL keeps its recorded hash and fails loudly instead of silently accepting new bytes.

**`ModelManager`'s root must agree with `sttModelRoot()`.** Both honour `OPEN_ROOM_MODELS`; when only one did, the manager downloaded to `~/.open-room/models` while the loader looked somewhere else and reported the model missing.

## UI conventions

shadcn/ui (Radix + Tailwind v4) for all components. Components are copied into the repo via the CLI and are ours to edit — modify them in place rather than wrapping them in adapters.

- `src/renderer/src/components/ui/` — shadcn-generated primitives. Edit freely; do not re-run `add` over a customized file without checking the diff.
- `src/renderer/src/components/` — app components composed from the primitives.
- Path alias `@/` → `src/renderer/src/` (note the nested `src` — that is electron-vite's renderer root). Declared in `electron.vite.config.ts`, `vite.config.ts`, `vitest.config.ts`, `tsconfig.json`, and `tsconfig.web.json`. `@shared/` → `src/shared/` is available to all three processes.
- Tailwind v4 is configured via the `@tailwindcss/vite` plugin and a bare `@import "tailwindcss";` in the renderer entry CSS. There is no `tailwind.config.js`, so `components.json` leaves its `tailwind.config` field as an empty string.
- **The window's title bar is drawn by the app, not the OS.** Windows paints its caption bar in the user's accent colour and a pale grey the moment the window loses focus, and none of it is reachable from CSS — so `createWindow` sets `titleBarStyle: 'hidden'` with a `titleBarOverlay` tinted to the palette, and `TitleBar` renders the strip. Two things are load-bearing: `TITLE_BAR_HEIGHT` must equal that component's height or the native buttons overhang the strip they are drawn on, and the strip must keep `app-region: drag` or the window cannot be moved at all. Anything interactive placed in there needs `app-region: no-drag` to escape the drag.
- **The brand mark lives at `src/renderer/src/assets/logo.png`**, cropped to its bounding box and scaled to 192 px tall — the supplied file was a 218×545 mark centred in a 1024×1024 canvas, which renders as a speck if used as-is. It is the *light* variant, a flat `#cfcfcf` on transparent, but only its alpha is used: `TitleBar` draws it as a `mask-image` on a span filled with `bg-foreground/85`, so one asset serves both themes. Size it by height with `aspect-ratio: 218 / 545`; it is about two and a half times taller than it is wide.
- **Light and dark are a setting, and `nativeTheme.themeSource` is the whole mechanism.** `theme` in settings is `system | light | dark` (default `dark`, because every install before the setting existed was dark by construction and an update must not flip anyone). Main hands it to `nativeTheme.themeSource`; Chromium then answers `prefers-color-scheme` in every window from that, and `followColorScheme` (`src/renderer/src/lib/theme.ts`, tested against fakes) toggles the `dark` class on the root element from that query, in both entry points, before React mounts. There is no theme IPC and neither HTML shell carries a class. What CSS cannot reach is set from `themeChrome` (`src/shared/theme.ts`): the window's `backgroundColor` and, on Windows, `setTitleBarOverlay`, re-applied on every `nativeTheme` `updated` event so an OS switch under "system" recolours the caption buttons. Those two hex values must stay twins of the palette's `--background` and `--foreground`. The light palette is shadcn's stock neutral set on `:root`; `color-scheme` is declared per theme block (`light` on `:root`, `dark` on `.dark`) so scrollbars and form controls follow. The overlay has a three-variable palette of its own in `overlay.css` (`--or-fg`, `--or-surface`, and the shadow pair), exposed as the `or-fg` colour so opacity modifiers work, because importing the main window's whole token set into an always-on-top window was the same mistake as importing Zod there. Verified in the dev app by driving `saveSettings`: the root class, the media query and the body colour flipped in both windows, in both directions, and "system" followed the OS.
- **The app icon is generated from `resources/brand/`, not hand-drawn.** `logo-light.png` and `logo-dark.png` are the canonical marks, cropped to their bounding boxes (218×545 each; the supplied files were centred in 1024×1024 with the mark occupying a fifth of it). Everything else is derived: `build/icon.png` (1024, the electron-builder master), `build/icon.ico` (7 frames, 16–256, each rendered at its own size rather than downscaled from one), `build/icon.icns`, and `resources/icon.png` (512, the runtime window and Linux icon). The recipe is a rounded-square tile — `#2c2c33`, inset 4%, corner radius 22.4% of the tile — with the *light* mark at 78% of the tile's height, centred.
- **The icon is a tile because a bare mark cannot work on both taskbars.** Measured at 16–64 px against both a dark and a light strip: the mark alone is invisible on one or the other, and a near-black tile disappears into a dark taskbar. `#2c2c33` is lifted far enough to separate from a dark taskbar while keeping plenty of contrast on a light one. If the tile colour is ever darkened to match the app background, check it at 16 px on a dark taskbar first — that is where it fails.
- **Scrollbars are styled globally in `main.css`, and the two ways of doing it are mutually exclusive.** From Chromium 121 `scrollbar-width`/`scrollbar-color` take precedence and switch `::-webkit-scrollbar` off entirely, so setting both silently loses the detailed one. This uses the pseudo-elements. `color-scheme` is separate and still needed: the palette lives in CSS variables Chromium cannot see, so without it the parts it owns — form controls, and any scroll container the pseudo-elements miss — render light on a black page. It is declared per theme block, not on `html`.
- **`vite.config.ts` exists only so the shadcn CLI can detect the project.** It looks for that exact filename and fails on `electron.vite.config.ts` with "could not detect a supported framework." The real build is driven by `electron.vite.config.ts`; keep the renderer settings in the two files in sync.
- **A long select list uses `<SelectContent scrollbar>`.** Radix's default `item-aligned` mode centres the selected item on the trigger, grows the box toward the window edge as you scroll instead of scrolling it, and hides the scrollbar; on the 28 Kokoro voices that read as a list that would not scroll. `scrollbar` switches to popper placement aligned to the trigger's left edge, caps the viewport at 18rem, drops the arrow buttons, and puts the scrollbar back. The last part has to be unlayered CSS in `main.css`: Radix hides it with an unlayered `<style>` tag, which no Tailwind utility can beat, and `scrollbar-width` goes back to `auto` rather than a value, since any other value switches off the app's `::-webkit-scrollbar` styling. Measured in the dev app: the box held at 288 px, the wheel and a dragged thumb both scrolled to Adam, and choosing him updated the trigger. Playwright attached over CDP forces `prefers-color-scheme: light`, so a dark-mode screenshot needs `page.emulateMedia({ colorScheme: 'dark' })`.
- **Pin the component base when adding:** shadcn v4 defaults to Base UI, but this project uses Radix. Init was `npx shadcn@latest init -b radix -p nova -y`.
- **The composer floats over the transcript; nothing sits under it.** It used to be a bordered strip below the scroller, which read as a separate panel. Now the working strip and the composer are the scroller's last child, `sticky bottom-0` with `mt-auto`, so a short transcript still puts the bar at the bottom and a long one scrolls up behind it. What keeps the bar legible over text: an 8-unit gradient above it fading to the page colour, a `bg-background/85 backdrop-blur-md` wash under the whole group, and the box itself opaque (`bg-background`, `dark:bg-card`) with a shadow. Measured in the dev app in both themes with a padded transcript: the group's bottom equals the scroller's, the last line fades under the bar, and the box stays a clear step off the wash. Two things the follow-the-tail logic needed once the bar was inside the scroller, both found by driving a turn: the follow effect used `scrollIntoView` on a sentinel, which aligns it with the viewport's bottom edge, exactly where the bar now sits, so every new row landed behind it (it sets `scrollTop = scrollHeight` now); and the pinned test's 80 px slack counts the floating group's height too, since a reader whose last message sits behind the bar is at the bottom in every sense that matters, and without it one unlucky scroll event unpinned the pane for good. The drop overlay moved out of the scroller and up to `z-20` so it covers the bar too.
- **The composer is one box with two layouts, and the wrap decision is measured, not read back.** Attach, textarea and send all live inside one rounded bordered container (the textarea itself is bare — the box carries the border and `focus-within` ring). One row while the draft fits beside the buttons; once it wraps, the textarea takes the whole first row (`order-first basis-full` under `flex-wrap`) and the buttons drop to a bottom row. Whether it wraps is decided by `wrapsAt` (`lib/composer.ts`) measuring the draft with a canvas against the *row* layout's width, never by reading the rendered height: the textarea is wider in the wrapped layout, so a borderline draft would fit again, flip the layout back, and oscillate forever.
- **The agent editor and settings dialog are static-backdrop: an outside click pulses instead of closing.** A stray click in the pane threw away half-edited agent config in the field. An inline "Unsaved changes" confirm bar was tried first and rejected as poor practice — it rendered at the bottom of a scrollable dialog, trapped no focus, and stacked two rows of similar-weight buttons. The convention for form dialogs (Bootstrap's "static backdrop"; MUI/Chakra/Atlassian equivalents) is that an outside click is not a close command at all: `useStaticDialog` (`hooks/use-static-dialog.ts`) prevents Radix's `onInteractOutside` and answers with a scale pulse (`.dialog-attention` in `main.css` — animates the `scale` property, which composes with the content's `translate` centering; a `transform` animation would fight it). Esc, the X, Cancel and Save all still close — deliberate gestures, so Cancel and Esc discarding without a prompt is intended. Applied to both dialogs so a click beside a dialog means the same thing everywhere.
- ESLint relaxes `explicit-function-return-type` and `react-refresh/only-export-components` for `components/ui/**` and `lib/utils.ts`. Those files are generator output; holding them to authored-code rules means fighting `shadcn add` every time. Formatting is still enforced via `npm run format`.
- Prettier ignores `*.md` — docs are hand-written prose, and prettier rewrites emphasis markers and collapses list boundaries.

## Testing

The high-value logic here is pure and easily tested: the SpeechBus, the voice-resolution fallback chain, the wake/phonetic matcher, the config Zod schemas, the capture reducer, the silence endpointer, `pipsFor`, `quota.ts`, `context-usage.ts`, `session-overrides.ts`, `speakableAsIs`/`shouldSpeakFallback` in `condense.ts`, and `agentQueryOptions`. TDD these. Anything that needs a microphone, a window or a subprocess should be a thin executor over one of them — that is why `VoiceController` takes all of its collaborators as dependencies. Each phase's "Done when" in `plan.md` names the tests that prove it.

**Prefer extracting a pure function to reaching into a private one.** `agentQueryOptions` was pulled out of `AgentSupervisor` for exactly this reason: the options it builds decide what an agent can reach and whose account it bills, and every way they can be wrong is silent — the agent still runs and still answers. Several documented decisions there had nothing checking them until the seam existed.

**A test that cannot fail is worse than no test.** Two in this repo passed for the wrong reason before being caught: a Windows-path case whose backslashes had collapsed into a newline, so a path rule was never exercised; and a regression guard proven only by deliberately reintroducing the bug it was meant to catch. Prove a new guard fails before trusting it.

**A green working tree does not prove a green commit.** Phase 5d went through twelve task reviews with every check passing, and its branch tip did not typecheck: staging files by name had committed hunks that imported `login.ts` and `claude-binary.ts` while those files sat untracked in the tree, so every run used them and nothing noticed. Before merging, prove the tip on a clean checkout — `git worktree add <dir> HEAD`, then typecheck, lint, test and build there. Do not junction `node_modules` into that worktree (see Gotchas); `npm ci` there is slower and safe.

**`voice-sink.test.ts` has one timing-sensitive interrupt case that fails perhaps one run in ten.** It passed on immediate rerun every time it was seen; a single failure there on an otherwise green suite is that, not a regression. Three consecutive full runs is the bar when it matters. **It now sits inside the release gate too**: the release workflow runs the suite once per OS leg, so roughly one tag in five fails spuriously — the v0.1.0 tag's second run did, on the macOS leg, while the same commit passed identical checks in two CI runs. The no-credentials remedy is to delete and re-push the tag (safe: it stays on the same commit, and the release is drafted rather than published, so a failed run is invisible to users). If re-tags keep happening, quarantine this one case from the CI-facing suite rather than loosening its timing — the timing is the assertion.

**CI runs on macOS too, so tests must not read `process.platform` implicitly.** Anything that branches on the platform takes it as a parameter and the tests pass `'win32'` or `'darwin'` explicitly — `resolveExecutable`, `isExecutableTarget` and `openInEditor` all do. A test that only passes on the machine it was written on is the same class of failure as a test that cannot fail.

Named bus tests that must exist: preemption upward only, progress-only expiry (a `question` queued behind a long `blocker` must still play), latest-progress coalescing, and burst collapse. The bus no longer prefixes speaker names, so the old prefix-suppression test is gone; what replaced it asserts the inverse — that no agent name reaches the audio, however long the gap or whoever spoke last.

## Gotchas

**`ANTHROPIC_API_KEY` silently wins over the subscription.** SDK auth precedence is cloud creds → `ANTHROPIC_AUTH_TOKEN` → `ANTHROPIC_API_KEY` → `CLAUDE_CODE_OAUTH_TOKEN` → interactive login. If that variable exists anywhere in the environment, agents bill API credits instead of the subscription. Strip it explicitly when spawning. Note the SDK's `env` option _replaces_ `process.env` rather than merging, so build the child env deliberately.

**`claude update` does not update the CLI agents run.** Agents spawn the binary inside `@anthropic-ai/claude-agent-sdk-<platform>-<arch>`, never the global install, so a "Claude Code 2.1.233 does not support this model; version 2.1.251 or newer is required" 400 from a new model means the SDK is behind, however current the terminal's `claude --version` is. The SDK's patch number is the CLI's: `0.3.273` bundles `2.1.273`. Bump the SDK and cut a release; there is nothing a user can do on their side. `.github/dependabot.yml` opens that bump as a pull request daily (the SDK only; everything else stays hand-updated), and since the pickers offer whatever the bundled CLI reports, merging it and tagging is usually all a new model needs.

**Never add native modules to the Electron process.** They belong in the voice sidecar. Anything requiring `electron-rebuild` in main is a design error.

**`globalShortcut` has no key-up event.** True hold-to-talk requires the sidecar's native key hook.

**`persistSession: false` makes a session unresumable.** Don't pair it with `resume`.

**Never junction `node_modules` into a git worktree.** `git worktree remove --force` follows a Windows junction into the real directory and deletes through it until it hits a path too long to remove — which is how `node_modules/.bin` and `@electron-toolkit` vanished from this checkout mid-session. The symptom is `npx` reporting `'prettier' is not recognized` while `node` itself still works. `npm ci` restores it; Electron's binary survived because `electron/dist` sits below the long-path failure point, but check it (`node node_modules/electron/install.js` if not).

**`File.path` is gone since Electron 32; `webUtils.getPathForFile(file)` is the replacement, and it only works in the preload.** It is exposed as `window.openRoom.pathForFile` and returns `''` for anything without a real path — a pasted image, a synthesized `File`. Callers must treat empty as "no path", never as a relative path.

**The CLI's own permission engine runs before `canUseTool`.** Read-only commands such as `git status` are auto-approved there and never raise a prompt in Open Room, whatever the agent's tool settings say; a permission-prompt test needs a command the CLI does not pre-approve. In `auto` mode the classifier sits in the same place, which is why `canUseTool` never fired for two Bash calls on Sonnet.

**Radix `Select` cannot hold an empty string as a value.** Optional selects ("no fallback model", "model default") need a sentinel constant mapped back to `''` in both directions. Binding `''` directly throws at runtime.

**`setIgnoreMouseEvents(true, { forward: true })` does not deliver mouse events to the overlay.** Measured: thirty scripted cursor moves across it produced zero `mousemove` events in its document. A click-through, non-focusable, always-on-top window gets nothing on Windows, so `:hover`, `mouseenter` and `mouseleave` never fire there and any hover affordance built on them silently does nothing — which is exactly how it fails, silently. Main polls `screen.getCursorScreenPoint()` every 60 ms instead and hit-tests it against a box the overlay reports (`useHitBox` → `overlayHitBox`), answering on `overlayPointer`. That same poll is the only thing that turns click-through off, and only while the cursor is genuinely over interactive content: leaving the whole 460×220 window clickable would swallow every click in a large rectangle above the taskbar.

**The overlay window never resizes.** It is created at fixed bounds large enough for its widest state — the expanded roster, the hovered transcript. Window resizing cannot be animated smoothly on Windows, so everything animates inside those bounds instead.

**A hidden window gets no `requestAnimationFrame` at all, and its timers throttle to ~1 Hz.** Measured on the overlay's exact window shape: 0 rAF frames and 2 `setInterval(16ms)` ticks per 2 seconds once `hide()` has been called, against 331 and 125 when visible. The overlay is hidden whenever there is no pill and no pip — which `pushHud()` arranges within a second of launch — so anything driven by its render clock stops there and never restarts. Always-on wake listening lives in this window and polls on rAF, so it started, ran until the first hide, and was silently dead for the rest of the session. `backgroundThrottling: false` in its `webPreferences` is what keeps that clock running; it is load-bearing, not a tuning knob. Note the failure is invisible from inside the renderer — the listener reports itself started and simply is never called again. The audio graph is never throttled (measured unchanged at 32 callbacks per 2 seconds while hidden), so moving the gate onto the AudioWorklet would remove the dependency entirely.

**A window created with `show: false` is not yet throttled** — measured at 273 rAF frames per 2 seconds before its first `hide()`. So this class of bug survives a naive test: the feature works until something hides the window once, and testing a freshly created window will never reproduce it.

**`webContents.send` before `did-finish-load` is dropped silently.** The overlay replays its last state and any queued capture signal on load for this reason; hotkey failures are pulled by the renderer on mount as well as pushed, because registration happens during `whenReady`, before any window has loaded. Any main→renderer message sent during startup needs one of those two treatments.

**The microphone is granted to the overlay and denied to everything else.** Electron approves permission requests by default, which would leave any window in the app able to open it. `session.defaultSession` gets explicit request and check handlers keyed on `OverlayWindow.owns()`, so a future feature that needs a permission fails at a line that says why rather than quietly inheriting an allow-all.

**The AudioWorklet is imported as `./pcm-worklet.ts?worker&url`.** The obvious `new URL('./pcm-worklet.ts', import.meta.url)` emits the TypeScript source verbatim as an asset and `addModule` chokes on it — in the packaged build only, since the dev server transpiles on the fly. The `?worker&url` form bundles it to a dependency-free IIFE and returns a URL relative to the importing chunk, which resolves under both the dev server and `file://`.

**Speech models load offline.** `stt.ts` sets `env.allowRemoteModels = false` and points `localModelPath` at the directory `ModelManager` populated, so acquisition keeps its checksum verification and resumable download instead of transformers.js quietly fetching its own copy into a second cache. Installed is not loaded, either: nothing loads the model on the capture path, so `transcribe` loads it lazily and main warms it at launch when voice input is on.

**There is no `window-all-closed` handler, deliberately.** The app is tray-resident; closing the last window must not quit it. `close` is prevented and the window hidden instead, which means an actual quit has to set `quitting = true` first or `app.quit()` hangs forever on a window that refuses to close.

**A tray-resident app needs `requestSingleInstanceLock`.** It is invisible, so the obvious way to "open" it is to launch it again — which without the lock starts a second process that fails to register any global hotkey (the first holds them), adds a second tray icon, and runs its own agents against the same files. `second-instance` shows the existing window instead. Windows also files a new tray icon into the overflow flyout rather than the visible tray until the user promotes it, so "the tray icon isn't showing" is usually not a bug.

**Assets used by main are `?asset` imports.** electron-vite emits them and rewrites the path, which works in dev and packaged alike; the tray and window icons both rely on it. Joining against `process.resourcesPath` would have to account for `asarUnpack` and would break silently when it did not.

**`src/overlay/` and `src/renderer/overlay-main.tsx` are listed explicitly in `tsconfig.web.json`.** Neither sits under `src/renderer/src/**`, so until they were added `npm run typecheck` never looked at them and reported green over unchecked code. Anything added beside them needs the same treatment.

**`overflow-y-auto` alone still produces a horizontal scrollbar.** CSS computes the other axis to `auto` when one axis is not `visible`, so a single pixel of horizontal overflow shows a scrollbar. Pair it with `overflow-x-hidden` unless the content genuinely scrolls sideways.

**Radix `ScrollArea` is unreliable inside a flex-sized parent.** Its viewport sizes itself with a percentage height that does not resolve against a parent sized by `flex: 1`, so content paints past the container and over anything below it. Inside a dialog body, use a plain `min-h-0 flex-1 overflow-y-auto` div. `ScrollArea` is fine where the parent has a definite height, as in the sidebar. A dialog also needs `overflow-hidden` on `DialogContent`, which is a grid with no clipping by default.

**Electron's postinstall can silently skip the binary download.** Symptom is `Error: Electron uninstall` from `electron-vite dev`, with `node_modules/electron/` missing `dist/` and `path.txt`. Fix: `node node_modules/electron/install.js`. Worth checking first whenever dev refuses to launch after a dependency change.

**Backslashes do not survive a Bash tool heredoc here, and Python's default encoding is cp1252.** Two ways an edit to a text file goes wrong silently on this machine. Every `\\` written in a Bash tool command arrives in the shell as `\`, quoted heredoc or not — measured three times in one session: a `'\\ '` check became `'\ '`, a regex `\r?` became `r?`, and a Python "fix" replaced text with itself. And `open(p, 'w')` in Python on Windows encodes as cp1252: an em-dash writes as one byte and corrupts a UTF-8 file, and a `→` raises `UnicodeEncodeError` *after* `'w'` has truncated the file — which is how `plan.md` was emptied and had to be rebuilt from session transcripts. Use the Edit/Write tools for anything containing a backslash or non-ASCII text; if Python must write a file, open it with `encoding='utf-8'` and never with a bare `'w'` on a file you cannot recreate.

**This package is CommonJS** — there is no `"type": "module"`. `__dirname` works directly in the main process and in config files; don't reach for `fileURLToPath(import.meta.url)` here.
